## 一、产品理念：设计权的归属

> 本节记阿哲 2026-11-12 的原话判断，是本子项目的出发点。

## 1.1 两种体验，各有代价

用户用我们平台的 AI，可以**自己主导对话的方向**。

| | 平台 AI 对话（wtt） | 景区导览小程序 |
|---|---|---|
| 设计权 | **留给自己** | **交给别人** |
| 自由度 | 高——想聊哪聊哪，随时改方向 | 低——设计师预设了路线与讲法 |
| 代价 | 要**付出精力**去思考、去表达 | 不用思考，**只是享受** |
| 风险 | **未必让自己满意**——自己不一定就了解自己的需求 | 设计师的美学表达未必合我口味，但通常不需我操心 |

**两端是互补的，不是替代关系。**

- wtt 平台这一端的价值：帮用户**发现**自己到底想要什么（动机挖掘本身就是这件事），代价是用户要投入对话精力，且结果依赖用户自我认知的准确度。
- 景区小程序那一端的价值：用户**不必思考**，直接享受设计师的美学表达。

## 1.2 这条理念对产品设计的约束

**因此 wtt 的角色不是「把行程塞进讲解小程序」，而是「把用户在 wtt 里澄清过的东西，交还给不想再思考的用户」。**

推论：

1. **注入的是「需求理解」，不是「行程指令」**。小程序端已经有设计师的路线编排；wtt 注入的是用户是什么样的人（同伴、节奏、兴趣、避开什么），让讲解版本和侧重对得上人。**不要抢设计师的活**——那既越界又会让设计师的美学表达被冲淡。

2. **注入必须能「什么都不注入」**。用户在小程序里是来享受的，不是来被打断的。如果画像很薄或缺失，小程序端应退回**通用优质讲解**，而不是硬套一个不合适的个性化。

3. **wtt 平台这一端的产出，要能被「不想思考」地消费**。这直接支持 §三 的结论：注入用结构化字段（可映射到讲解版本/侧重标签），不是一段需要用户再消化的散文。

4. **用户在小程序端的自由，是「换个讲解版本」的自由**，不是「重开一轮对话」的自由。设计上传入的画像不能有交互成本。

## 1.3 与本项目卡点的关系

现有判断（见 PLAN.md、.pms.yml）：平台能控的只有「画像 → 结构化 context」半段，「设备 → 接收」半段由景区/小程序方主导，是商业问题不是技术问题。

本节理念不改变这个结论，但**解释了为什么这个半段值得谈**：

- 小程序方拿到画像，能让用户**不思考就享受**——这正是景区想要的产品形态（参考文档里千灵山「9.9 元解锁全套讲解」、万佛湖「AI 智能客服 7×24 全天候应答」都是这个逻辑）。
- wtt 拿到的是「用户理解需求」的能力出口——用户在 wtt 里付出的思考精力，一次沉淀成画像，之后每次到景区都能被复用。

**两边都受益，且不需要谁牺牲自己的定位。**

## 二、边界（本子项目做什么、不做什么）

> **阿哲 2026-11-13 钉死的分工**：现在是**模拟景区**；以后真合作，小程序由**景区来做、景区来备案**。
> 所以 `mvp/miniprogram/` 是**模拟景区端的参考实现**，用来验证「平台侧契约跑得通」，
> **不是交付给景区的代码**。景区按自己的工程规范重写小程序，平台侧契约不变。

| 做（wtt 平台侧） | 不做（景区侧） |
|---|---|
| 登录端点、token 签发/校验/失效/撤销 | 小程序本体开发与上线 |
| 画像 → 结构化 context 的组装与导出 | 备案、类目、算法备案、微信认证 |
| 注入契约与字段映射（画像 → 讲解标签/侧重） | 内容安全双向检测、AI 生成标识落地 |
| 合同/协议层面的技术对接口 | 知识库建设、讲解稿、LLM 接入与选型 |

> 备案、类目、算法备案、内容安全（`security.msgSecCheck` 双向检测）、AI 生成标识、真机与弱网测试——这些按参考文档都是**景区/小程序方的主体责任**。本项目不承担，但接口契约要保证景区方能履行。
>
> ⚠️ 由此推论：小程序端那些 `wx.setStorageSync` / 免密恢复逻辑都只是**参考实现**。真正要保证的是**平台侧 token 契约**（能签发、能校验、能失效、能撤销）。

## 二·补、方案一：下次免密 ✅ 已实现（2026-11-13）

**阿哲定**：先做方案一。

**方案**：小程序端存 token（**不存账密**），下次进来拿 token 问平台还认不认，认了就免密。

| 侧 | 落点 |
|---|---|
| 平台 | `_TOKEN_TTL` 从 300 秒改为 **30 天**（对齐主项目 `auth.COOKIE_MAX_AGE`）；新增 `GET /api/auth/verify`（有效返 `{valid:true,user,expires_in}`，失效返 `{valid:false}` **不是 401**） |
| 模拟景区端 | `miniprogram/utils/session.js` 封装 `save/read/clear`；`onLoad` 调 `tryRestore()`；登录成功 `session.save()`；失效/退出 `session.clear()`；失效**静默**退回账密框 |

**为什么单独加 verify 端点**：不能拿 `/api/context` 当探活——它会顺带把画像组装出来，小程序启动时调它等于没经用户确认就刷出讲解，语义和开销都不对。

**为什么不存密码**：token 有 TTL、可撤销、只承载一次会话授权；`wx.setStorageSync` 没有 httponly，JS 能读，存密码等于永久泄露。

**微信账号隔离**：`wx` storage 按 (小程序 AppID + 微信用户) 由微信 runtime 隔离，同设备换微信不互通、同微信换设备不共享。所以方案一**不需要额外建微信账号体系**——那是 R2 一键绑定才要的事。

**验收**：单测 20/20（含 `verify` 有效/失效/不暴露 context/TTL 够长 4 条）；e2e 场景 E 全过——首次账密 → 关页重开免密恢复 → 不再出现账密框 → 退出登录后不再免密。

> ⚠️ 仍是内存实现：服务端重启后 token 失效，小程序会静默退回账密。这是有意保留的降级演示，不是缺陷；生产须持久化、可撤销、绑真实身份、HTTPS。
> ⚠️ 换设备/清缓存/卸载小程序仍要重输账密。要做到「换设备也免密」得升 R2（openid 绑定），属 D2 待定。

## 三、设计决策

### D1. 注入的 context 里不留用户原话，只导出概括 ✅ 已定

**阿哲 2026-11-13 定**：不留原话，只导出概括。

- **背景**：`summary` 是画像里唯一的用户原话保留形态（PROFILE_FIELDS 定义「保留他自己的说法与语气」）。平台自己政策是「不存对话原文」，但 summary 事实上保留了原话，只是没存全量。把它交给第三方小程序，等于把用户原话交给第三方。
- **结论**：`profile.summary` **留库内，绝不出平台**。出平台的只有：
  1. 结构化字段（`public_profile` 后 pop 掉 `summary`）
  2. `abstract` —— 由结构化字段拼出的一句话概括（`profile_summary`），不含任何自由文本
- **这是结构性约束，不是选项**：没有开关、没有 query 参数能把它打开。`build_system_prompt` 根本不读 `profile.summary`；`_useful()` 也把它剔掉。测试里有一条专门验证「传 `include_summary=true` 也不生效」。
- **MVP 落地**：`mvp/platform/server.py` 的 `/api/context` 返回 `schema: wtt.context/v0.2`，prompt 里是「游客画像概括（由结构化字段生成，非用户原话）：…」。

### D2. 账号打通走哪条路 ⬜ 待定（MVP 走 R1）

**先钉一条事实**：微信小程序的 `wx.request` **不携带平台 cookie**（没有浏览器 cookie jar，且 `wtt_auth` 是 `httponly` + `samesite=lax`）。所以「平台账号登录」的本质是：小程序拿一个**平台签发的 token**，之后每次请求带上。三条路的区别只在「凭什么签发」：

| 路线 | 首次 | 之后 | 要不要微信身份 |
|---|---|---|---|
| **R1 + 存 token（方案一，MVP 采用）** | 输一次账密 → 存 token | 免密（凭本地 token），**换设备/清缓存要重输** | 不用，storage 隔离够 |
| **R2 微信 code 换 token**（「一键绑定」） | `wx.login()` 拿 code → 平台换 openid → 查绑定表 → 已绑定则直接签发 token | 免密（凭 openid 换 token），**换设备仍免密** | 要，得建绑定表 + 微信身份字段 |
| **R3 微信 unionid** | 平台办微信开放平台资质，用 unionid 做跨应用统一身份 | 同上 | 要资质、要主体，最重 |

**平台现状（2026-11-13 实读）**：`users` 表只有 `id/email/password_hash/nickname/created_at/last_login/role/org_id`，**没有任何微信身份字段**；没接 `wx.login`、没建绑定表、没微信开放平台资质。所以「在微信中保存平台登录态」这个形态**目前不存在**——不是已有而没用上，是要新建。

「一键绑定」真要成立的形状：

```
wx.login() → code → 平台后端换 openid
  → 查绑定表：openid 已绑 user_id？
      是 → 直接签发 token（免账密）
      否 → 走一次 R1 账密，把 openid 绑到该 user_id，此后免登
```

**首次仍要账密**这一条跑不掉——绑定关系得有一次可信的 establishing。要不要接微信、要不要办资质，是阿哲的决策，不替他定。

> ⚠️ 修正记录：RESEARCH-20261112.md §3.4 初版把 R1 写成「web-view/直调登录」、把 R2 写成「一次性票据」，标签混了两条不同的东西。以上表为准。
> ⚠️ MVP 初版没有账密登录、只做了票据壳子且不验密码 —— 这是设计失误，2026-11-13 已补成真 R1（`mvp/platform/server.py` 复用主项目 `auth.verify_password` 做 constant-time 校验）。

### D3. 「画像 → context」demo 的完成标准 ✅ 已定

按「能跑通的 MVP」做：平台侧导出 + 小程序侧登录与渲染 + 端到端验收，不碰上线。成果在 `mvp/`，见其 README。
