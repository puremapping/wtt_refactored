# 对话-行程闭环设计（v0.3）

**日期：** 2026-09-18
**目标：** 让对话与行程不再是两段，而是一个闭环——AI 能看见行程、操作行程，用户能就行程继续对话。

---

## 一、核心变化

```
【v0.2 现状】
  对话 →（攒画像）→ 用户点按钮 → 生成行程 → 右侧展示（对话与行程脱节）

【v0.3 目标】
  对话 ⇄ 行程（双向）
    · 用户对 AI 说「生成行程」→ AI 直接触发 → 右侧出现
    · AI 能看到右侧行程 → 用户就行程提问，AI 基于实情回答
    · 用户要求修改 → AI 说明改法 → 用户确认 → 落实 → 右侧更新
```

---

## 二、交互规则（已与阿哲确认）

| 场景 | 行为 |
|---|---|
| **生成行程** | **AI 自动判断**：用户说「生成行程」「看看行程」「给我排一下」即触发，无需额外确认 |
| **修改行程** | **必须先确认**：AI 说明要改什么 → 用户点确认 → 才落实 |
| 撤销 | 不做（确认机制已提供保障） |

---

## 三、技术方案：Function Calling

**已验证：`glm-4-flash` 支持 function calling**
（实测返回 `finish_reason: tool_calls`，参数抽取正确）

### 3.1 工具定义

```python
TOOLS = [
    {
        "type": "function",
        "function": {
            "name": "generate_itinerary",
            "description": (
                "为用户生成一日行程。当用户明确表达想看行程/生成行程的意愿时调用。"
                "注意：调用前应确保已了解用户的旅行动机。"
            ),
            "parameters": {
                "type": "object",
                "properties": {
                    "hours": {
                        "type": "integer",
                        "description": "行程时长（小时），1-12。用户没说则省略。"
                    },
                    "note": {
                        "type": "string",
                        "description": "本次生成的补充说明（可选）"
                    },
                },
                "required": [],
            },
        },
    },
    {
        "type": "function",
        "function": {
            "name": "propose_modify_itinerary",
            "description": (
                "提议修改当前行程。当用户对现有行程表达不满或提出调整要求时调用。"
                "**注意：这只是提议，需要用户确认后才会真正执行。**"
            ),
            "parameters": {
                "type": "object",
                "properties": {
                    "action": {
                        "type": "string",
                        "enum": ["replace", "remove", "add", "reorder", "regenerate"],
                        "description": (
                            "replace=换掉某站, remove=删除某站, add=加一站, "
                            "reorder=调整顺序, regenerate=重新生成整条"
                        ),
                    },
                    "target": {
                        "type": "string",
                        "description": "操作对象（景点名），regenerate 时留空"
                    },
                    "reason": {
                        "type": "string",
                        "description": "修改原因（给用户看的说明）"
                    },
                },
                "required": ["action", "reason"],
            },
        },
    },
]
```

### 3.2 为什么用 `propose_modify` 而不是 `modify`

**工具名本身带 `propose`**，语义上就告诉模型「这是提议」。模型在对话里会自然地说「我建议把 XX 换成 YY，可以吗？」，而**真正的执行由用户点击触发**。

这比让模型自己判断"该不该确认"可靠——**小模型判断力弱，用工具设计约束它。**

## 四、数据流

```
┌─────────────────────────────────────────────┐
│ 用户消息                                      │
└──────────────┬──────────────────────────────┘
               ▼
┌─────────────────────────────────────────────┐
│ conversation.chat(session_id, text,          │
│                   current_itinerary)   ← 新增│
│                                              │
│  ① 抽取画像（独立调用，只给用户原话）          │
│  ② 生成回复 + 可能返回 tool_calls            │
│     · 带完整历史                             │
│     · 带当前行程摘要（让 AI「看得见」右侧）    │
│     · 带 tools 定义                          │
└──────────────┬──────────────────────────────┘
               ▼
        有 tool_calls？
        ├─ 无 → 返回 reply
        └─ 有 ↓
┌─────────────────────────────────────────────┐
│ generate_itinerary   → 服务端立即执行        │
│                        返回 itinerary 给前端  │
│ propose_modify       → 返回 proposal 给前端  │
│                        等用户点确认           │
└─────────────────────────────────────────────┘
```

### 4.1 AI 如何「看见」行程

每轮对话时，把当前行程**摘要**拼进 system 消息：

```
【当前行程】
动机：恢复/逃离
时长：8 小时  |  共 4 站  |  25.7 公里

1. 09:00 京都第一瀑景区（3A·密云区）人流 0
2. 10:16 北京天门山旅游风景区（3A·密云区）人流 1
3. 11:37 捧河湾自然风景区（3A·密云区）人流 0
4. 14:00 神堂峪自然风景区（3A·怀柔区）人流 2

风险：各站点均无地铁直达，建议自驾或打车
```

**要点**：给摘要不给全量 JSON（省 token，且模型不需要那么多细节）。

## 五、修改的落实

用户点确认后，前端调 `POST /api/itinerary/modify`：

```json
{
  "session_id": "...",
  "action": "replace",
  "target": "神堂峪自然风景区",
  "reason": "太远了"
}
```

服务端按 action 处理：

| action | 处理 |
|---|---|
| `replace` | 从候选池里选同类中最近的一个替换，重算时间线 |
| `remove` | 删掉该站，重算 |
| `add` | 从未入选的推荐里挑一个合适的插入 |
| `reorder` | 重跑 TSP |
| `regenerate` | 换一批候选重生成 |

**所有修改都要重算时间线**（到达时间会变）。

## 六、时序图（完整闭环）

```
用户: 最近太累了想找个人少的地方
  AI: [抽画像] 恢复/逃离 ✓
  AI: 听起来你想找个安静的地方。是一个人还是…

用户: 一个人。生成行程吧
  AI: [抽画像] companions=独自
  AI: [tool_call] generate_itinerary()
  → 服务端执行 → 右侧出现行程
  AI: 给你排好了，都是密云的小众自然景区，人很少…

用户: 最后那个神堂峪太远了
  AI: [看得见行程，知道最后一站是神堂峪]
  AI: [tool_call] propose_modify(replace, "神堂峪自然风景区", "距离较远")
  AI: 神堂峪确实离前三个有点远（约 30 公里）。可以换成
      XX 景区，同区域、人也不多。要改吗？
  → 前端显示 [确认] [取消]

用户: [点确认]
  → 服务端执行 replace → 重算时间线 → 右侧更新
```

## 八、风险

| 风险 | 应对 |
|---|---|
| 小模型乱调工具 | 工具名带 `propose` 语义约束；服务端校验参数合法性 |
| 模型不该调时调了 | prompt 明确触发条件；日志记录所有 tool_calls 便于排查 |
| 行程上下文太长 | 只给摘要（站名+时间+区+人流），不给完整 JSON |
| 修改后时间错乱 | 所有修改统一走「重算时间线」 |
