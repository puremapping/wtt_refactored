# 网站的标签与导航系统

**Where to Travel v0.5** · 本文盘点站点当前的导航/标签实体，并给出建议。

> ⚠️ **先说结论：这个网站目前几乎没有标签与导航系统。**
> 全站是「单一对话入口」，没有可浏览的内容目录。
> 本文如实列出「有什么 / 没有什么」，再讨论该不该建。

---

## 一、现状盘点

### 1.1 全站入口清单（共 2 个页面 + 4 个 API）

```
GET  /              主界面（对话）
GET  /admin         数据看板（内部）
GET  /docs          FastAPI 自动文档
GET  /api/health    健康检查
```

**没有任何内容页。** 没有景区列表、没有分类页、没有搜索页。

### 1.2 页面上的全部可点击元素

**主界面（`/`）顶栏：**

| 元素 | 位置 | 行为 |
|---|---|---|
| `#stats` | 顶栏左 | 纯文本（「212 个景区 · 217 条人流」），**不可点** |
| `#user-box` | 顶栏右 | 「登录」链接 / 「昵称 + 退出」 |
| `#btn-history` | 顶栏右 | 打开历史抽屉（登录后可见） |
| `#btn-restart` | 顶栏右 | 清空当前对话重开 |

**主界面（`/`）正文：**

| 元素 | 位置 | 行为 |
|---|---|---|
| `#messages` | 左栏 | 对话流（AI 生成，非导航） |
| `#starters` | 左栏底 | **4 条固定引导语**（见下） |
| `#input` + `#btn-send` | 左栏底 | 输入 |
| `#profile` | 右栏上 | 画像面板（AI 抽取结果） |
| `#cta-block` | 右栏中 | 「看行程」按钮 |
| `#result-block` | 右栏下 | 行程结果（叙述/评估/时间线/地图） |

**浮层：** `#auth-modal`（登录注册）、`#history-drawer`（会话列表）、`#loading`

### 1.3 唯一接近「标签」的两处

**① 引导语（`STARTERS`）—— 硬编码的 4 条，不是标签**

```
「最近太累了，想找个安静的地方」
「带爸妈玩一天，他们腿脚不太好」
「一个人随便逛逛，拍点照片」
「预算不多，想省钱玩一天」
```

**性质：** 这是**意图示例**，点一下就发出去当用户消息，**不是分类或筛选器**。
用户不能「浏览」它们，只能「说」它们。

**② 画像面板的字段标签 —— 是对 AI 抽取结果的展示，不是导航**

```
主动机  [恢复/逃离]  4/5
次要    文化/沉浸
时长    约 8 小时
同伴    父母
节奏    适中
兴趣    古建筑、咖啡馆
避开    爬山
必去    —
```

**性质：** **只读展示**。用户不能点它筛选，也不能改它（只能通过对话改）。

### 1.4 数据层有的标签（但界面上没用）

数据库里**有丰富的分类字段**，**但没有任何界面暴露它们**：

| 字段 | 取值数 | 界面上能按它筛吗 |
|---|---|---|
| `district` | 北京 16 区 | ❌ 不能 |
| `level` | 5A/4A/3A/2A/1A | ❌ 不能 |
| `ticket_free` | 0/1 | ❌ 不能 |
| `price_high/low` | 连续值 | ❌ 不能 |
| `saturation` | 0-100 | ❌ 不能 |
| 场所气质标签 | `nature`/`indoor`/`serious` | ❌ 不能（仅内部打分用） |

**唯一用到它们的地方是 `/api/attractions?district=xxx`** —— 但那是**调试接口**，前端没调用。

## 二、结论：现在有什么

```
                  有没有   说明
─────────────────────────────────────────────────────
全局导航           ❌      无导航栏
内容目录（列表页） ❌      无
分类标签           ❌      无
筛选器             ❌      无
搜索框             ❌      无
面包屑             ❌      无
Tab / 分段控件     ❌      无
─────────────────────────────────────────────────────
顶栏按钮（3 个）   ✅      功能入口，非导航
引导语（4 条）     ✅      硬编码意图示例
画像字段展示       ✅      只读，不可交互
数据层分类字段     ✅      存在但界面未暴露
```

**一句话：这是一个「只有对话」的产品 —— 没有可浏览的信息空间，也就没有导航和标签的需要。**

---

## 三、这是设计选择，还是缺失？

**要先分清「有意不做」和「漏了」。**

### 支持「有意不做」的理由

**产品的核心主张就是「先问为什么去，再告诉去哪」。**

```
传统旅游站：  浏览 → 筛选 → 挑一个     （用户先有明确需求）
这个产品：    对话 → 挖动机 → 我替你挑  （用户需求模糊）
```

**如果加了分类浏览，等于承认「用户知道自己要什么」** —— 那这个产品的差异化（动机驱动）就没意义了，会退化成又一个景区黄页。

**MVP 阶段不做列表页，是合理的取舍。**

### 支持「缺失」的理由

**① 匿名用户没有「退出路径」**

现在必须一路聊到底才能拿到结果。用户若只想「随便看看北京有什么」，**没有轻量入口**。

**② 数据资产闲置**

212 个景区、16 个区、5 个等级、实时人流 —— **这些是花了力气搞来的真实数据，界面上一个都没露出**。数据来源的可靠性是这个项目的卖点，却不可见。

**③ 无法验证「推荐是否合理」**

用户拿到行程后，**看不到「还有哪些没被选中」**，也就无法判断推荐质量。**只看一版结果，等于只能信任或否定**。

**④ 对话是唯一交互，成本高**

LLM 调用要钱要时间。**「按区筛选」这种确定性需求，不该走 LLM。**

## 四、建议（按优先级）

### 优先级 1：行程页加「其他候选」列表

**不做新页面，只在右栏结果区下方补一块。**

```
#result-block
├── #narrative    叙述
├── #assessment   强度评估
├── #timeline     时间线
├── #map          地图
└── #alternatives ← 新增：本次没选中的其他候选（3-5 个）
                    每项带「为什么没选」的理由
```

**好处：** 让推荐**可证伪**（用户能看到备选），复用现有数据，不加新页面。

### 优先级 2：顶栏加「景区速查」抽屉

**沿用 `#history-drawer` 的交互模式**（右侧滑出），不新建路由。

```
[景区速查]  ← 顶栏新按钮
├── 按区： 东城 / 西城 / 朝阳 / ... (16)
├── 按等级：5A / 4A / 3A / ...
└── 按人流：低 / 中 / 高
```

**好处：** 数据资产露出；给匿名用户一个「不聊也能看」的入口；
**确定性需求不消耗 LLM 调用**。

### 优先级 3（暂缓）：独立列表页

**不建议现在做。** 理由见上「有意不做」——
**一旦有了完整列表页，产品就变成景区黄页，动机驱动的差异化被稀释。**

**等有了真实用户反馈再定。**

## 五、如果要做，标签怎么设计

**沿用现有数据字段，不自造新维度。**

| 标签组 | 取值 | 来源 | 多选 |
|---|---|---|---|
| 行政区 | 东城/西城/朝阳/海淀/丰台/石景山/门头沟/房山/通州/顺义/昌平/大兴/怀柔/平谷/密云/延庆 | `district` | ✅ |
| 等级 | 5A/4A/3A/2A/1A | `level` | ✅ |
| 门票 | 免费 / 收费 | `ticket_free` | ✅ |
| 场所气质 | 自然 / 室内 / 严肃 | `_kind()` 派生 | ✅ |
| 人流 | 空闲(<20) / 适中(20-60) / 拥挤(>60) | `saturation` 分档 | 单选 |

**设计约束（与现有体系一致）：**

1. **标签只做筛选，不做分类** —— 一个景区可同时是「朝阳区+4A+免费+自然」，**多值是常态**
2. **不要用目录装标签** —— 别做「按区/朝阳区/景区」这种树，区只是标签之一
3. **筛选结果直接进对话上下文** —— 用户筛完可以接着聊「这几个里哪个适合带爸妈」，筛选与对话不是两套系统

**第 3 条是关键：** 标签系统不该是并列的第二入口，**而该是对话的补充输入**。
