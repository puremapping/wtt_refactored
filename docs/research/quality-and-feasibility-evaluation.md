# 景点质量与行程可行性的客观评估方法（数据贫乏条件下）

**调研日期：** 2026-10-29
**问题设定：** 数据源只有官方 A 级景区名录（名称/等级/区县/地址/经纬度/门票是否免费），**没有评分、评论、用户行为**。要判断「这个景点值得推荐」（= 去完了真觉得值），而非「用户会点」。
**方法：** 官方标准与协议原文 + 实测 API（本机 `.env` 的高德 key）+ 学术文献（引出处见文末）。

| 能力 | 状态 | 依据 |
| --- | --- | --- |

**由此得出一条硬架构约束**（下文 §5 的方法都要遵守）：

> **平台自有库里只能存「我们自己的推断产物」，不能存高德返回值。**
> - 可落库：等级、门票、名录身份、我们自算的 `visit_minutes` 估计、我们自算的通勤时间估计（秒数）、拥挤度评分、标签。
> - 不可落库：`rating` 值、`opentime_week` 原文、POI 坐标/地址、路径距离。
> - 因此运行时要**在线取营业时间与路径**（缓存只放进程内、短 TTL），并把「评分」转成我们自己的**离散档位**（如「高/中/低」）而非原值。

这条约束不是合规洁癖——它直接决定了 §1 里「用评分做排序」能不能做：**能做实时冷路径，不能做离线模型特征与数据集。**

### 1.2 A 级评定到底代理了什么——必须知道它的结构，才知道它能用在哪

GB/T 17775 的等级由**三张表**共同决定，缺一不可（2003 版与 2024 版口径一致）：

| 表 | 内容 | 满分 | 5A 门槛 |
| --- | --- | --- | --- |
| 细则一 服务质量与环境质量 | 旅游交通 130 / 游览 235 / 旅游安全 80 / 卫生 140 / 邮电 20 / 旅游购物 50 / 综合管理 200 / 资源与环境保护 145 | 1000 | 950 |
| 细则二 景观质量 | 资源吸引力 65（观赏游憩价值 25、历史文化科学价值 15、珍稀奇特 10、规模与丰度 10、完整性 5）+ 市场影响力 35（知名度 10、美誉度 10、市场辐射力 10、主题强化度 5） | 100 | 90 |
| 细则三 游客意见 | 现场游客满意度抽样 | 100 | 90 |

关键判读：

1. **细则一占绝对权重，但装的是「好用不好用」（厕所、标识、停车、医护），不是「好看不好看」。** 5A 要 950/1000，意味着一个整洁便利但平淡的地方也能拿高分。用它做质量主分，会把「基础设施型」景区抬得过高。
2. **细则二才是「值不值」的那一维**，但 5A 门槛只有 90/100，且九项因子靠评定组打分后算术平均——**粗颗粒、易受主观影响**。
3. **细则三曾被大量地方折算为「游客意见」纸质问卷**，实际可得性为零。
4. 2024 版（GB/T 17775-2024，2025-03-01 实施）的实质变化对推荐系统有直接意义：新增「文旅融合」「智慧旅游」，把游览细化为「游览设施 + 游览服务」，**并在旅游安全中增加了景区承载量控制、高峰期游客流量控制要求**——官方自己承认了「拥挤」是质量维度。
5. 因此：**A 级适合当「可达性/可靠性闸门」和「资源稀缺度的低分辨率版本」，不适合当「值不值」的唯一分。** 真正区分「值不值」的，是 S2（身份稀缺性）与 S4/S5（负面信号）。

### 1.3 可落地构造：不依赖评分的「价值分」

不用任何平台评分，只用公开名录 + 官方公示，可以构造一个可解释、可审计的离散分：

```
value_score = w_id * identity_tier          # 身份稀缺性（主，50%）
            + w_grade * grade_prior         # 等级先验（25%，A 级→分数，单调）
            + w_uniq * uniqueness           # 类型稀缺性（15%，同城同类同等级有多少家）
            + w_free * accessibility_bonus  # 免费/低票价（10%，反常识但有效：低摩擦 → 完成率高）
            - penalty_disciplinary          # 复核降级/通报/问题清单 → 强负分
            - penalty_crowd_risk            # 承载量小 + 饱和指数高 + 无分时预约 → 负分
```

`identity_tier` 的赋值依据（全部可公开核验）：
- Tier A：世界遗产（中国共 60 项，2025-07 西夏陵列入后）或国家级风景名胜区（9 批共 244 处，国务院公布）
- Tier B：4A/5A + 全国重点文物保护单位 / 国家级旅游度假区等
- Tier C：仅 3A 以下
- 交叉验证：高德 `keytag`（如故宫返回「5A景区」+ 类型含「世界遗产」）与 Wikidata 的 `P1435`（遗产地位 = Q9259 世界遗产）双向校验，防名录名称变体（「故宫博物院」vs「明清故宫」）漏配。

**为什么把「身份稀缺性」当主项而不是等级**：等级是相对的、可被"补设施"达成；世界遗产/国家级风景名胜区的判定走的是「突出普遍价值（OUV）」与国务院审定，评判的是**资源本体的不可替代性**——这正是「去完了觉得值」的因果上游。且这两个名录体量极小（60 / 244），与我们的名录做内连接的开销几乎为零，命中率就是质量信号本身。

### 1.4 关于「OTA 评分能不能合法拿」——结论

| 源 | 能不能 | 说明 |
| --- | --- | --- |
| 大众点评 | ❌ | 有明确判例：大众点评诉百度不正当竞争（浦东法院 2016 一审、上海知产法院 2017 二审维持），判赔 300 万+23 万。裁判要旨：「未违反 robots 协议不等于可任意使用」，**未经许可大量完整使用点评信息达到实质替代程度**构成不正当竞争 |
| TripAdvisor | ❌ | Caching Policy：除 Location ID，任何内容不得缓存/复制/存储/索引 |
| Google Places | ⚠️ | 只有 `place_id` 可长期存；评分评论不得存储；大陆覆盖不足 |
| 高德 | ⚠️ 在线可读、离线不可 | 协议 3.5/3.4；且明确禁止用于模型训练 |
| **官方名录 / 政府公示 / Wikidata** | ✅ | 无授权障碍，可入库、可训练 |

**所以：数据贫乏不是缺陷，而是把方案逼到了正确的位置——用「稀缺性 + 制度信号 + 时序负面事件」替代「评分均值」。** 后者在旅游里本来就假：一个 5A 景区 4.8 和 4.9 的差别，比不上它当天有没有排队两小时。

## 2. 行程可行性怎么验证

### 2.1 问题正确的形式：不是 TSP，是带时间窗的定向问题（TOPTW）

TSP 要求「走遍所有点并最短」；旅游的真实问题是「时间预算固定，选一个子集，使总价值最大」。学术上对应 **Tourist Trip Design Problem（TTDP）**，其主流建模是 **Orienteering Problem（OP）**，加时间窗即 **TOPTW（Team OP with Time Windows）**，加多天即多日 TOPTW。Ruiz-Meza & Montoya-Torres（2022, *Operations Research Perspectives* 9:100228）系统综述了 102 篇文献，结论：**OP 是 TTDP 领域应用最广的模型**。

这决定了「可行性」不是事后检查，而是**可行性本身就是目标函数的约束集**：

```
max  Σ value_i · x_i                       # 价值来自 §1.3，不是评分
s.t. 到达时刻 t_i 落在 [open_i, close_i - visit_i]     # 营业时间窗（含停止检票时刻）
     t_{i} + visit_i + travel_{ij} ≤ t_j               # 真实通勤
     t_0 ≥ start,  t_n + visit_n ≤ end                 # 一天的起止
     Σ visit_i + Σ travel_ij + Σ rest_k ≤ budget       # 体力预算（含午餐/休息块）
     travel_ij 用真实路网时长（非直线距离）
```

**多天行程的额外约束**：跨天不能重复计费/重复入园、住哪里的锚点固定、每天必须有一个「重头戏」不排在最后半天（见 §5 末条）。

### 2.2 时间预算用什么样的数——「真实时长」从哪来（实测）

| 手段 | 实测结果 | 能不能落库 |
| --- | --- | --- |
| 高德 `v3/direction/walking` | 返回 `distance` + `duration` + 逐段 `walk_type` | ❌ 只在线用 |
| 高德 `v3/direction/transit/integrated` | 公交/地铁综合换乘 | ❌ 只在线用 |
| `walk_type` 用途 | 阶梯(20)/地下通道(3)/过街天桥(4)/地铁通道(5)/公园(6)/广场(7)/索道(10)/观光车(15) 计数 → 可算**体力成本**而非只有时间 | 派生统计可留 |

**体力成本模型（可自研，不依赖第三方）**：把路径按 `walk_type` 加权，得到「等效步行分钟」：

```
effort_minutes = Σ（普通路段分钟 × 1.0 + 阶梯段 × 1.6 + 上下坡/索道 × 1.3 + 过街天桥/地下通道 × 1.2）
```

这个「等效分钟」是我们自算的，可以落库做模型特征。**这是在数据贫乏条件下难得的合法特征工程口子。**

**景点内部停留时长（`visit_minutes`）**——最大的未知，也是最该自己校准的量：
- 冷启动默认值（对应 5A/4A/3A 的「可游览规模」）：**150 / 90 / 60 分钟**，大型山岳/主题公园另行放大（如长城类 180–240）。
- 校准方法见 §4：用「行后反馈」的「计划停留 vs 实际离开时间」回归，逐景区修正。**这一列一旦有数据，就是本系统最值钱的资产**——它比任何评分都更能预测「一天能不能走完」。

### 2.3 三个必须做成硬校验的量（可直接写进测试）

1. **开放时间校验**：`opentime_week` 实测能返回丰富的自然语言（周一闭馆、停止检票时刻、旺季淡季切换、园中园单独时间、按周次分段变化）。**必须解析，必须当成一等情况**：故宫周一全天关闭、16:00 停止检票在旺季——把故宫排在周一下午的行程，是 0 分方案而不是「略差」。
   → 解析后的结构：`[{date_range, weekdays, open, last_entry, close}]`，无法解析时**降级到保守默认并标注不确定性**，不许静默当作 24h 开放。
2. **预约可得性校验**：故宫「不售当日票，参观前 7 日 20:00 开售」——这是比开放时间更早的硬墙。把它当成 `bookable_from` 字段：行程日期距今 < 7 天的故宫方案，直接标红。
3. **步行/交通真实性**：直线距离在景区群（如颐和园—圆明园—香山之间）会严重低估；必须用路网时长。实测故宫→天坛 5.68 km 需 75.8 分钟——这种「看着近、走起来一小时」的段落，就是「看起来合理但实际很糟」的主要来源。

### 2.4 一个可落地的校验器设计（不依赖学术求解器）

数据贫乏 → 候选池小（北京 212 家）→ **不需要元启发式**，用「模拟 + 枚举局部改进」就够，且完全可解释：

```
for each candidate itinerary (top-K by value/ 天):
    simulate(day):
        t = start
        for stop in sequence:
            arrive = t + travel(prev, stop)         # 真实路网时长
            if arrive outside [open, close - visit]: → 不可行，原因=营业/闭馆
            if arrive < bookable_ready: → 不可行，原因=预约未开/已满
            t = arrive + visit + queue_penalty(stop, hour)   # 拥挤 → 排队时间
            fatigue += effort(arrive_travel)
            if fatigue > fatigue_budget: → 不可行，原因=体力
            if lunch_window_passed and not eaten: → 扣分，原因=用餐错位
        if t > end: → 不可行，原因=超时 risk_high
    score = feasible ? Σvalue - λ·waiting_time - μ·fatigue : 0
```

输出的不是「一个方案」，而是**「可行 + 每个 compromise 的显式说明」**（如「少了 X，因为周一闭馆；Y 排队预计 40 分钟」）。这与 AlterAtlas（Huang, Du, Zhang, arXiv 2607.16565）的实证发现一致：**用户判断一个行程规划「成功」，标准是「高效且舒适地到达了所有锚点」**，中间停靠点是可交换的填充物；且用户明确要求「告诉我哪里不得不妥协」。

## 3. 旅游推荐系统的学术评估方法与电商的差异

### 3.1 现有评价体系的三个层次

| 层次 | 典型指标 | 在旅游里的问题 |
| --- | --- | --- |
| 评分预测精度 | RMSE / MAE | 需要显式评分，且**旅游没有稳定评分分布**（一次性体验、无重复购买）。CEUR Vol-1685《Challenges in Recommender Systems for Tourism》直言：主流指标都建立在显式反馈上 |
| Top-N 排序 | Precision@K / Recall@K / NDCG / F1 | 需要「用户真实点击/到访」做 ground truth；旅游没有。POI 场景的实证（*Information Technology & Tourism*, 2021, 10.1007/s40558-021-00214-5）表明：**精度高的系统上线后常被感知为「没什么用」，因为缺新颖性** |
| 行程级 | 推荐行程 vs 真实行程的集合/序列匹配（如 Halder 等的 Precision/Recall/F1 over POI set，I-AIR 等沿用） | 依赖 Flickr/GeoLife 等带时空戳的轨迹源；国内基本不可采 |

### 3.2 旅游与电商的四点本质不同，各自改变评价设计

1. **低频 + 高单价 + 高承诺**：单次决策的失败成本极高（一天浪费、门票/交通沉没）。→ **评价重心从「平均精度」转向「最坏情况/可行性」**：一条不可行行程的代价 >> 一批平庸推荐的代价。指标应是 **feasibility rate、must-see 达成率、worst-case 超时分钟**，而非 NDCG。
2. **体验型、事后才知道值不值**：反馈延迟到行程结束后，且是「整体记忆」而非「逐项打分」。→ 需要**行后（post-trip）**才有的标签；行前点的赞是意图，不是价值。
3. **有强空间/时间约束**：评价必须验证约束满足，而不只是内容相关性。→ 评估集应是**约束可验证的行程**，不是（用户，景点）对。
4. **口碑受峰值-终值规则支配**：Lin（2026, *Journal of Hospitality & Tourism Research*, 10.1177/10963480251337338）用实时体验抽样（ESM）证明：**游客的效价与满意度符合 peak–end rule；时长与开头无显著影响；极端负面瞬间对忠诚度的影响大于正向峰值**。→ 一条行程末尾塞一个 90 分钟排队，会把前面所有亮点抹掉。**评估必须显式惩罚「结尾体验」**。

### 3.3 可落地的替代评估框架（无用户行为也能用）

| 指标 | 定义 | 需要什么数据 | 现在能落地吗 |
| --- | --- | --- | --- |
| 硬可行性率 | 通过 §2.4 模拟校验的行程占比 | 营业时间 + 路网 | ✅ 立刻 |
| 锚点达成率 | must-see 集合中被排入的比例（AlterAtlas 的用户判据） | 用户声明 | ✅ 立刻 |
| 时间余量分布 | `end_slack = end - 实际结束时刻` 的分位数；负值即超时 | 同上 | ✅ 立刻 |
| 疲劳负载 | 等效步行分钟总和 / 用户档位 | 自算 | ✅ 立刻 |
| 结尾质量 | 末位景点的 value_score 与预期等待时长 | 本系统 | ✅ 立刻 |
| 拥挤暴露 | Σ 各点预计等待 | 饱和指数 / 承载量 | ✅ 北京即时序 |
| 多样性 / 新颖度 | 类型熵、与「同城 top-10 大众路线」的重合度 | 名录 | ✅ 立刻（重合规线 = 不新颖） |
| 行后实际 vs 计划偏差 | 停留时长偏差、舍弃率、迟到率 | **只有行后反馈能给** | ⏳ 需先埋点 |
| 离线排序精度（NDCG 等） | — | 需真实到访 | ❌ 现阶段不建议自欺 |

**建议的验收口径**（写进 PLAN 的验收判据）：
```
可行性：100 条随机需求 → 模拟校验通过率 ≥ 95%，且失败项全部有明确原因码
锚点：must-see 达成率 ≥ 90%
时间：p90 超时 ≤ 15 分钟；无负 slack（硬）
结尾：行程末站不得是「预计等待 > 30 分钟」的点
```

## 4. 「去过之后」的反馈怎么拿

### 4.1 学界共识：这是最贵也最缺的标签

- 传统做法（CEUR Vol-1685）：RMSE/MAE 需要显式评分；旅游需要「以最小侵入方式」测满意度——手段建议包括社交媒体、拍照、显式点赞/点踩。
- 体验抽样法（ESM，Lin 2026）：行程中实时自报效价/唤醒/满意度，能还原 peak–end 结构，但研究成本极高（需要日内多次打扰），不适合产品化。
- 智能旅游工具的系统评估（SEPRA, academia.edu/126092504）：主张**在线期评（每个游客访问中）+ 离线期评（每条 POI 路径结束后）**双段式，明确点出「真实游客介入的测试阶段成本高」，所以要把评估做便宜。

### 4.2 产品界的做法与效果

| 做法 | 谁在用 | 效果/要点 |
| --- | --- | --- |
| 购买后 + 行程后两段问卷 | WeSki（Survicate 案例） | 明确区分「下单时」与「回来之后」两触点，因为预订与体验不同期，合并问会污染 |
| 行后问卷极短化（3 题 1 分钟） | Mailpro、Surveyapp、QuestionPunk 模板 | 共识：游客回来后没耐心，长问卷完成率崩 |
| 行后单点追问「最好/最糟的一刻」 | QuestionPunk（AI 追问模板） | 正好对上 peak–end rule，比「总体 1–5 分」信息量高 |

**关键结论：行后反馈的价值不在「再给一个分」，而在「拿到可以校准的物理量」**——计划停留 vs 实际停留、舍弃了谁、哪里排了队。这些量能直接回填 §2.2 的 `visit_minutes` 与排队模型，比任何星级都有用。

### 4.3 本项目的行后反馈设计（低成本、可闭环）

在「行程完成后」触发**一次**极短交互（≤60 秒，3 个动作）：

1. **打勾：哪些去了、哪些没去**（→ 舍弃率、`visit_minutes` 回填）
2. **滑一下：哪一站最不值 → 给时长**（→ 真实停留时长，用于校准；同时天然产出 value 标签）
3. **一句话：最糟的一刻是什么**（→ peak–end 的「end」检测；也是拥挤/摆渡车的证据）

落库形态（都是我们自产数据，无授权问题）：

```sql
trip_feedback(trip_id, poi_id, planned_min, actual_min, visited bool,
              abandoned bool, worst_poi bool, worst_moment_text, created_at)
```

校准公式（简单可解释，不引入 ML）：
```
visit_minutes(poi) = median(actual_min) over feedback where visited=true
                   ← 若无样本，回退到 §2.2 的等级默认值
queue_penalty(poi, hour) = p75(actual_departure - planned_departure) 按小时分箱
```
**样本量 < 5 时不覆盖默认值**（防 1 个极端用户污染全库）。

## 5. 已知的坑：看起来合理但实际很糟的推荐形态

按「危害 × 在我们数据下是否易犯」排序。前 5 条在有名录+路网的条件下**一定会犯**，必须做成硬校验。

| # | 坑 | 为什么看起来合理 | 实际后果 | 对策（可落地） |
| --- | --- | --- | --- | --- |
| K1 | **把热门扎堆**（同一天塞多个 5A） | 都是高价值 | 排队 + 人挤 + 提前闭园（16:00 停止检票），末站体验崩塌；peak–end 抹掉全天 | 每天**最多 1 个 Tier-A 锚点**；第 2 个起需通过排队预算校验 |
| K2 | **忽略开放时间/闭馆日** | 名录没有时间字段，顺手当全天开放 | 周一去故宫 = 直接报废一天 | `opentime_week` 解析 + 未知时保守降级并标注 |
| K3 | **忽略预约墙** | 有票就能去 | 故宫提前 7 日 20:00 放票、不售当日票；八达岭强制预约 | `bookable_from` 模型；到期不足以成行 → 换点或明确告知 |
| K4 | **距离近当交通方便** | 直线 5 km | 实测故宫—天坛 75.8 分钟步行；景区群之间无穿行道路要绕 | 一律用路网时长；同城直线/路网比 > 2 的点对触发「交通不便」告警 |
| K5 | **把「可去」当「值去」** | 名录里 4A 占比高，全推 | 清单冗长、平庸景点稀释体验，用户感知「没什么用」（IT&T 2021 的新颖性结论） | value_score 严格分档 + 同城同类只留 1–2 家（uniqueness 项） |
| K6 | **摆渡车/景交车被当步行** | 大景区内部靠车 | 排队 30–60 分钟、线路不科学（文旅部 2026 点名龙虎山、长白山、天柱山、稻城亚丁、崂山） | 景区内 `walk_type` 15（观光车）单独计排队+车程；参考官方摆渡车问题名单 |
| K7 | **山岳型低估体力** | 只看人次与距离 | 台阶/索道是真实体力瓶颈，第 3 站就废 | 等效步行分钟（§2.2）+ 硬疲劳预算 |
| K8 | **把「顺路」排成回头路** | 地图上都在同一区 | 进出园单向（故宫午门进、神武门/东华门出）、单行道、步行街无法穿行 | 用景点出入口（POI 的 children：检票处/入口）而非中心点做路径端点 |
| K9 | **末站排「需要兴奋」的点** | 填补空档 | 结尾疲劳 + 排队 → 记忆里只剩这个 | 末站选「低门槛、可随时走」的点；惩罚末站等待 |
| K10 | **用餐与休息错位** | 时间表排满 | 13:30 还没吃饭、带娃无厕所（AlterAtlas 用户原话） | 在 11:30–13:30 之间强制插入休息块；疲劳预算里预留 |
| K11 | **跨天重复计费/重复入园** | 连续两天同一区 | 门票重复、体力重复消耗 | 跨天去重 + 每天必须有独立锚点 |
| K12 | **「小时数 → 点位数」硬映射** | 1h=3 点、8h=11 点（ITINERA `TIME2NUM`） | 完全忽略景区尺度差异与通勤，是「看起来能走完」的根源 | **废弃该映射**，改用 `Σ(真实通勤+visit+rest) ≤ budget` 的模拟校验 |
| K13 | **用高德评分做排序特征并落库** | 有分不用白不用 | 违反 3.5/3.4；一旦做数据集/训练即违约 | 只在线读、只用于阈值否决、只存离散档位 |
| K14 | **用 OSM 当中国路网基础** | 开源免费可存 | 大陆人行道/景区内路完备度不足，步行时长会系统性偏短 | 仅在无高德 key 时兜底，并对时长加保守系数 |
| K15 | **只评估意图（点没点）不评估完成（去没去）** | 有点击日志就做排序评估 | 把系统优化成「好看不好走」 | 用 §3.3 的可行性/达成率指标做验收；点击率仅作辅助 |

## 6. 结论：在只有官方名录的条件下，能做到什么程度

**能做的（今天就可落地，且证据充分）**

1. **值不值的代理**：用「身份稀缺性（世界遗产 60 / 国家级风景名胜区 244）+ 等级先验 + 类型唯一性 + 官方负面信号（复核降级、问题多发通报）」造 value_score。不是评分，但对「去完了觉得值」的因果链更近，且完全合规、可审计。
2. **可行性的硬校验**：在线取 `opentime_week` 与 `direction/walking`，做营业时间窗 + 预约墙（`bookable_from`）+ 真实通勤 + 体力预算的模拟校验。**这一步把推荐系统从「内容相关」升级为「约束满足」，是本项目性价比最高的投入。**
3. **拥挤度的客观量化**：北京独有的「重点景区饱和指数」+ 5A 承载量/瞬时承载量 → 排队预算，直接对冲 K1。
4. **行程级评估的替代指标**：硬可行性率、锚点达成率、时间余量分位数、疲劳负载、结尾质量。不用 NDCG 自欺。
5. **行后反馈闭环**：3 个动作换回 `visit_minutes` / 舍弃率 / 最糟一刻，回填后 `visit_minutes` 成为独家资产。

**做不到的（要诚实标注）**

- 单景点「好玩」的细粒度区分：A 级评分细则粗、高德评分区分度低（几乎全 4.7–4.9）。→ 只能给档位与理由，不能给「87.3 分」这种假精度。
- 离线个性化排序的精度评估：没有到访标签。→ 换用流程指标 + 小规模人工/专家评（AlterAtlas 用 51 对行程的专家评估，是可参照的廉价范式）。
- 全国范围内的高频人流：除北京外基本拿不到。→ 用承载量做静态拥挤先验，置信度标注降低。

**一句话架构建议**：**把「质量」建在不可替代性上（名录身份 + 官方负面事件），把「可行」建在真实约束上（路网时长 + 营业时间 + 预约 + 体力），把「好」留给行后反馈慢慢校准。** 三者都是自产数据，能落库、能训练、能审计；高德只当实时查询的仪表，不当数据底座。
