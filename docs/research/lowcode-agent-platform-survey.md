# 低代码 Agent 平台：开源方案调研

**日期：** 2026-10-15
**背景：** 阿哲的想法 —— 做一个供各地文旅（省/市/县）工作人员**自己搭建文旅智能体**的低代码平台，智能体跑在平台上。
**本文只做技术选型调研，不立项。**

---

## 一、结论先行

**有三条路，推荐顺序：**

| 方案 | 许可证 | 能不能商用/多租户 | 判断 |
|---|---|---|---|
| **A. Coze Studio（自建）** | Apache-2.0 | ✅ **可以** | **最适合做底座** |
| **B. Langflow（自建）** | MIT | ✅ 可以 | 更偏「编排工具」，缺租户/发布能力 |
| **C. Dify（自建）** | 魔改 Apache-2.0 | ❌ **明确禁止多租户** | **不可用**（见下） |
| D. n8n | Sustainable Use | ❌ 有商业限制 | 不适合 |
| E. Flowise | 部分商业许可 | ⚠️ 企业功能需付费 | 部分可用 |

**核心判断：**

> **没有现成开源项目能直接当「文旅低代码平台」用。**
> 它们解决的是「怎么搭建 agent」，**没有解决「怎么做多租户 + 谁能发布到哪儿 + 质量谁验收」**。
> 这些恰恰是文旅平台的核心。

**所以正确的做法不是「选一个装上」，而是「选一个当底座，在它上面加业务层」。**

## 三、逐个评估

### A. Coze Studio —— 推荐当底座

**来源：** 字节跳动把 Coze（扣子）的**核心引擎开源**，Apache-2.0。

**它有什么：**

```
✅ Prompt 编排
✅ RAG（知识库）
✅ Plugin（插件）
✅ Workflow（可视化工作流）
✅ 应用模板
✅ 可视化调试与发布
✅ Go + TypeScript，可私有化部署
```

**为什么适合：**

1. **许可证干净** —— Apache-2.0，商业可用，可改可分发
2. **它就是「无代码搭 agent」这个形态本身** —— 你想做的低代码平台，它已经解决了 80% 的通用部分
3. **中文生态** —— 字节出品，中文文档与模型适配好
4. **Go 后端** —— 部署轻，单机可跑

**风险：**

| 风险 | 说明 |
|---|---|
| **更新停滞** | 最后推送 2026-07-29，**已近 3 个月没动** —— 可能是「开源一版就完」 |
| 租户模型 | 需要实测确认是否支持多租户（这是你的核心需求） |
| 二次开发成本 | Go + TS 双栈，改动需要两套技能 |
| 商业化承诺 | 字节为什么要开源？后续会不会断供？ |

**必须先验证：** 部署一遍，看它的**用户/租户模型**能不能满足「各地文旅各是一个独立租户」。

### B. Langflow —— 适合做原型，不适合做平台

**MIT 许可，15.5 万 star，社区最活跃之一。**

**定位：** 可视化**编排 LLM 流程**（拖节点连线），偏「开发者工具」。

**不适合做文旅平台的原因：**

- 缺**多租户**（没有工作区/组织隔离）
- 缺**发布渠道**（搭完是个流程图，不是能对外用的产品）
- 缺**权限体系**（文旅局工作人员与管理员没有区分）
- 缺**知识库管理**的完整链路

**它的价值：** 如果想**先验证「低代码搭文旅 agent」这个交互长什么样**，用 Langflow 最快出原型。

### C. Dify —— 不可用（许可证卡死）

**这是本次调研最重要的发现。**

Dify 的 LICENSE 原文：

```
Dify is licensed under a modified version of the Apache License 2.0,
with the following additional conditions:

1. ... Should the conditions below be met, a commercial license must be
   obtained from the producer:

a. Multi-tenant service: Unless explicitly authorized by Dify in writing,
   you may not use the Dify source code to operate a multi-tenant environment.

   - Tenant Definition: Within the context of Dify, one tenant corresponds
     to one workspace. The workspace provides a separated area for each
     tenant's data and configuration...
```

**翻译：未获 Dify 书面授权，不得用其源码运营多租户环境。**

**而你的平台本质就是多租户** —— 每个文旅局是一个租户，数据必须隔离。

**所以 Dify 不能作为商业平台底座。** 除非：
- 向 Dify 购买商业授权（费用与条件需谈）
- 或者你的平台做成「单租户、一家文旅局一套部署」—— 那运维成本爆炸

**这条要提前知道，否则做完才发现要付授权费。**

### D. n8n —— 许可证不适合

**Sustainable Use License**（非 OSI 认证）：

- 主分支以外的代码**不授权**
- 含 `.ee.` 的文件**必须持有 n8n 企业许可**
- 允许内部业务使用，**但转售/托管服务受限**

**你的平台是「给别人用的托管服务」** —— 踩线。

### E. Flowise —— 部分可用

**主体宽松，但 `packages/server/src/enterprise` 目录是商业许可。**

**问题：** 企业功能（多租户、权限、审计）**正好在付费区**。
而你需要的恰恰就是这些。

## 四、关键认知：现成方案缺的正是你要的

**把这些平台的能力和你需要的对比：**

| 能力 | Dify | Coze Studio | Langflow | **你的平台需要** |
|---|---|---|---|---|
| 可视化搭 agent | ✅ | ✅ | ✅ | ✅ |
| RAG 知识库 | ✅ | ✅ | ✅ | ✅ |
| 工作流编排 | ✅ | ✅ | ✅ | ✅ |
| **多租户隔离** | ❌ 收费 | ? | ❌ | **✅ 必须有** |
| **角色权限（编辑/审核/发布）** | 部分 | ? | ❌ | **✅ 必须有** |
| **跨 agent 路由**（主智能体调地方） | ❌ | ❌ | ❌ | **✅ 核心差异** |
| **准入质检**（自动验收数据质量） | ❌ | ❌ | ❌ | **✅ 核心差异** |
| **统一话术不变量**（动机七类） | ❌ | ❌ | ❌ | **✅ 核心差异** |

**结论：通用能力可以复用，差异化必须自建。**

## 五、如果要做，推荐架构

### 分层

```
┌───────────────────────────────────────────────────┐
│  ④ 文旅业务层（自建）                              │
│     · 动机七类统一话术                             │
│     · 准入质检（数据完整性/可复现/不编造）          │
│     · 跨城市路由                                   │
│     · 文旅专用模板（景区/路线/节庆）               │
├───────────────────────────────────────────────────┤
│  ③ 平台层（自建）                                  │
│     · 多租户（一文旅局=一租户）                     │
│     · 角色：编辑员 / 审核员 / 平台管理员            │
│     · 发布审批流                                   │
│     · 用量统计与配额                                │
├───────────────────────────────────────────────────┤
│  ② Agent 引擎（复用 Coze Studio）                   │
│     · Prompt 编排 / RAG / Plugin / Workflow        │
│     · 可视化调试                                   │
├───────────────────────────────────────────────────┤
│  ① 模型层                                           │
│     · GLM / Qwen / DeepSeek（可切换）              │
└───────────────────────────────────────────────────┘
```

### 为什么这样分

**② 层是「别人已经做好的通用能力」** —— 自己重造是浪费。
**③④ 层是「你的业务核心」** —— 也是竞品抄不走的部分。

**这个架构和你现在的项目是同一条路：**
现在的 `cities.py`（城市注册表）+ 动机引擎 + 编排算法，
**正好是 ④ 层的雏形**。抽象做好，将来直接搬。

## 六、必须先验证的三件事（动手前）

### 1. Coze Studio 的租户模型

**部署一遍，看：**
- 能不能开多个工作区（租户）
- 租户间数据是否真隔离
- 有没有角色权限

**如果它只支持单租户** → ③ 层要从头写，成本大幅上升。

### 2. 二次开发的真实成本

**Go 后端 + TypeScript 前端。**
- 加一个新 API（比如质检接口）要改两处
- 你的现有代码是 Python —— **存在语言分裂**

**要评估：是接受 Go+TS 双栈，还是找一个 Python 系的底座。**

### 3. 字节是否持续维护

**最后推送 2026-07-29，近 3 个月无更新。**
去 GitHub Issues / Discussions 看官方是否回应，判断这是「长期项目」还是「开源一版」。

## 七、我的判断

**这个产品值得做，但现在不具备开工条件。**

**三个理由：**

1. **底座未验证** —— Coze Studio 的租户模型是否满足，没实测过，这是架构的地基
2. **客户未验证** —— 文旅局愿不愿意用低代码自己搭，是商业假设，不是技术问题
3. **主体未验证** —— 你现在的单城市闭环还没跑通真实用户

**建议的最小路径：**

```
第 1 步（1-2 天）：部署 Coze Studio，实测租户/权限/发布能力
        ↓ 如果租户不可用
第 2 步：评估「自建平台层 + Langflow 当引擎」的替代方案
        ↓ 如果可用
第 3 步：用 Coze Studio 搭一个「北京文旅」agent 做技术验证
        ↓ 验证通过
第 4 步：才谈多租户与业务层
```

**在第 1 步完成前，所有架构设计都是纸上推演。**

## 附：许可证速查（做商业平台前必看）

| 许可证 | 商用 | 多租户 SaaS | 改代码 | 必须开源改动 |
|---|---|---|---|---|
| **MIT / Apache-2.0** | ✅ | ✅ | ✅ | ❌ |
| 魔改 Apache（Dify） | ✅ | **❌ 需授权** | ✅ | ❌ |
| Sustainable Use（n8n） | 内部 ✅ / 托管 ❌ | ❌ | ✅ | ❌ |
| BSL | 多数 ❌ | ❌ | ✅ | 时限后转开源 |
| GPL-3.0 | ✅ | ✅ | ✅ | **✅ 必须** |

> ⚠️ **做平台（给别人用）和做应用（自己用）的许可证要求完全不同。**
> 「Apache-2.0」意味着可以拿去开公司；「魔改 Apache + 多租户限制」意味着
> **能自用，不能开平台**。这一条最容易被忽略。
