# 推荐系统的客观效果评估：指标体系、在线实验、满意度量化与冷启动

> 项目：wtt_refactored（旅游推荐）
> 撰写：2026-10-29
> 视角：**回答「推荐结果真的准吗——用户去了之后觉得值不值」**，不是回答「模型分数高不高」。
> 证据分级：`[实测]` 我本人跑过的计算 / `[一手]` 论文原文或厂商官方博文 / `[二手]` 转引或社区描述 / `[推论]` 我的判断，未经实验。

## 0. 先说结论（可直接执行的部分）

1. **现系统的根本问题不是「缺评分数据」，而是把「景区等级」当成了相关性的代理，并且用它承担 40% 权重。** 景区等级是一个**几乎无方差、且与个体偏好无关**的特征：5A 对所有人都是 5A。一个特征如果对所有用户在每个 query 上都克隆出同一个值，它在排序里贡献的就不是「个性化」，而是**把所有用户的推荐都推向同一批头部景区**——这是 order-preserving 的 constant bias，会把个人化的部分整体压平。
   → 评估体系的第一件事，不是补指标，而是**先量出「等级塌缩」到底有多严重**（见 §5.1，用方差/覆盖率就能量）。

2. **平均星级（4.x 星）在这个领域不可用作相关性标签。** 评论分布是 **J 型**（买后才评 → 正向偏差；极端才评 → 中间缺失），均值的统计前提（单峰或对称双峰）不成立 [一手，Hu/Zhang/Pavlou, CACM 2009]。用均值当 rel，等价于把「大家都去过的 5A」标成高度相关——**这正是系统塌缩的机制来源**。见 §3.2。

3. **小候选集（K=5~10）里，Precision@K 和 MRR 基本是失效指标**；有意义的只有 **NDCG@K**（保留序信息、能承受分级相关）和 **分级召回**，以及**不依赖标签的质量指标**（见 §1.3 实测）。

4. **在任何用户行为数据之前，唯一可信的评估方式是「专家标注 + 一致性校验 + 对评分器本身的校准」**——而这里最容易被忽略的一步是：**用人工标注去校准 LLM 裁判，并报告 kappa，而不是直接相信 LLM 打分**。见 §5.3。

5. **仅靠离线指标不能判断推荐好坏，这是有明确工业证据的，不只是「业内共识」。** Booking.com 对 150 个上线模型做了事后分析：离线指标的提升与 RCT 中的业务指标提升**不相关**（23 组对比、46 个模型，Pearson r = −0.1，90% CI [−0.45, 0.27]）[一手，KDD'19]。他们给离线指标的定性是：**「offline metrics are only a health check」**。

## 1. 离线评估指标体系

### 1.1 四个指标各自的适用条件（学术定义 + 判断）

| 指标 | 数学形态 | 适合什么 | 不适合什么 |
|---|---|---|---|
| **Precision@K** | top-K 里相关条目 / K | K 大（≥20）、且「多推几个也损失不大」的场景（搜索、商品列表、新闻流） | **K=5 且候选总量就 5~10 时几乎恒等于 1**，没有区分度（§1.3 实测） |
| **Recall@K** | top-K 命中的相关 / 全集相关 | 有明确「该出现的东西必须出现」的召回约束 | 全集相关数未知或本身就是 5 个时，退化成 Precision 的另一种写法 |
| **MAP** | 各相关位置的 P@i 再平均 | 多相关条目、要「全都找到且都靠前」（TREC 检索传统）[一手，Stanford IR Book] | 相关集很大且无差别时过于乐观；对「一个超级相关 + 一堆中等的」不敏感 |
| **MRR** | 第一个相关项位置的倒数 | **只有一个正确答案**的场景：问答、知识库检索、单一需求满足 | 推荐**天然是多答案**的（5-10 个候选），MRR 会把「第 2~5 名也很好」全部丢掉 |
| **NDCG@K** | 分级相关性的位置折扣累积 | **分级相关（1/2/3 星）、且位置重要**——**本项目最匹配的指标** | 无分级标签时退化为二元的；对「所有条目都中等好」的列表不敏感（见 §1.3 的 C 案例） |

**为什么 NDCG 对本项目最匹配：**
- 旅游推荐本来就该是**分级相关**的：「必须去」/「值得去」/「顺路可以」/「别去」——这四档不是二元的。NDCG 是唯一原生吃分级标签的常用指标。
- 5-10 个候选里，**头部位置的价值差异极大**（用户真的会按第 1 名决定去哪）。NDCG 的 log 折扣正好表达这个。

**NDCG 的两个工程坑（必须在意）：**
1. **增益函数 `2^rel - 1` 会把 top-1 挤爆。** 见 §1.3 实测：列表 A（一个 3 分 + 四个 2 分）与列表 D（两个 3 分 + 三个 2 分）NDCG@5 只差 0.002（0.908 vs 0.906），**原因是 A 的顶部那个 3 分已经吃掉了绝大部分 DCG，D 的第二个 3 分被折扣到几近无贡献**。想表达「多件都值得去」时，`2^rel - 1` 会失明。替代：**linear gain**（`rel` 直接当增益）或 **α-NDCG / N-NDCG**（见 §1.4，但注意实测的反例）。
2. **IDCG 的取法（「理想列表」怎么算）会直接改变绝对值。** 常见三种：全库理想、候选池内理想、K 内 ideal。**同一个算法换一种 IDCG 定义，分数可以差 20 个点以上**——所以**代码里必须写死一种，且不许跨版本比较绝对值；只比较同一 IDCG 定义下的相对变化**。

### 1.2 对「每次只推 5-10 个候选」的产品，哪些指标有意义

**用一句话判据：K 小 → 只看顺序，不看覆盖率。**

- ✅ **NDCG@5 / NDCG@10（分级相关，linear gain 或 rel 直接当增益）** — 主指标。
- ✅ **分级召回（按档统计）：top-3 里「必须去」档的命中率** — 这是真正对应「用户会不会觉得值」的代理：必去的东西没进前三，用户就白跑一趟。
- ✅ **Pairwise 正确率（Bradley-Terry / 成对比较准确率）** — 在无绝对分数标注时更稳（§5.3），且天然适合「哪个更值得去」的专家判断。
- ❌ **Precision@5**：候选池只有 5-10 个时几乎没有变化空间（实测 P@5 恒为 1.0，见下）。
- ❌ **MRR**：只有「唯一正确答案」才用得上；旅游推荐不是。
- ⚠️ **MAP**：会随「相关定义」剧烈漂移，且和 NDCG 高度重复；**不必同时用两个**。
- ❌ **RMSE / MAE（评分预测误差）**：那是「预测用户会给几分」的指标，不是「推荐得对不对」的指标。**它衡量的是模型对已知评分的拟合，不是排序质量**——本项目一个评分数据都没有，这个概念从根上不适用。

### 1.3 `[实测]` 小候选集下各指标的数值行为

脚本：`research/eval_metrics_probe.py`（纯标准库，`python research/eval_metrics_probe.py` 可直接复现）。

设相关阈值 rel≥2（「值得去」以上），K=5：

| 列表 | 内容 | Prec@5 | Recall@5 | MAP | MRR | NDCG@5 |
|---|---|---|---|---|---|---|
| **A** 理想 | `[3,2,2,2,2,1,1,1,1,0]` | **1.000** | **1.000** | **1.000** | **1.000** | 0.908 |
| **B** 必去的被「安全 4A」挤到第 3 | `[2,2,3,2,2,...]` | **1.000** | **1.000** | **1.000** | **1.000** | **0.766** |
| **C** 全是 3.8~4.1 星的「中不溜」 | `[2,2,2,2,2,2,2,2,2,2]` | **1.000** | 0.500 | **1.000** | **1.000** | 0.649 |
| **D** 两个拔尖 + 三个还行 | `[3,3,2,2,2,1,...]` | **1.000** | **1.000** | **1.000** | **1.000** | 0.906 |

**这张表就是本项目评估体系的核心论据：**

- **Precision@5、MAP、MRR 在四个列表上全部并列 1.000**——包括那个「把必去项挤到第 3 名」的 B 和那个「全是庸品」的 C。**在小 K 下它们对「推荐质量」完全不敏感。**
- **只有 NDCG 分得开**（0.908 / 0.766 / 0.649 / 0.906）。
- **C 案例最要命**：全是中不溜的列表拿到了 100% 精确率和 100% 平均正确率，说明**任何基于阈值二值化的指标，都会把「全平庸」判为完美**。这正是当前系统「5A 都合格 → 打分都不错 → 但用户去了觉得没劲」的数学复刻。
- **D vs A 暴露了 `2^rel-1` 的失明**：两个拔尖 vs 一个拔尖，NDCG 只差 0.002。→ 如果想奖励「多件都值得去」，**必须换 gain 函数**。
- **K 敏感性实测**：同一张 A 列表，P@1..P@5 恒为 1.00，P@10 掉到 0.50——**Precision@K 的数值基本由 K 和候选池大小的比值决定，不由排序质量决定**。

### 1.4 多样性/新颖性指标：要加，但别指望它是解药

推荐质量不只有「相关」，还有「别给 5 个都是古镇」。标准工具：
- **α-NDCG**（Clarke et al., 2008）——同一"方面（aspect）"的重复命中被折扣；
- **N-NDCG / novelty-NDCG**（Clarke et al., 2008）——只算第一次出现的方面。

`[实测]` 但我的数值探针给出一个**反例**：

| 列表 | α-NDCG(α=0.5) | N-NDCG | 语义 |
|---|---|---|---|
| A 一个拔尖 + 四古镇 | **8.580** | 7.000 | 主题单一但有一个强项 |
| D 两个拔尖（徒步 + 古镇） + 三个还行 | **4.533** | **11.417** | 主题分散且有两个强项 |

**α-NDCG 反而把「两个不同方面的拔尖」判得比「一个方面拔尖」低**——因为 α 折扣惩罚的是"同 aspects 内的重复"，而 A 的所有项都在同一 aspect 里时，折扣基数被算成了重复计数。**这是实现约定问题**（`0^0=1` 与"首个命中不折扣"的约定不同，各家实现不一致，直接抄会算错）。
→ **结论：多样性指标的口径极易出错，不要自己实现后就直接用于决策；要么用成熟库（`ranx`、`ir-measures`），要么改用更笨但可靠的口径**：**top-5 的主题分布熵**（比如「5 个候选落在几个不重复的类别里」），它可解释、不会有 α 陷阱。

## 2. 在线评估（A/B）设计

### 2.1 除 CTR 以外，什么能反映「推荐真的好」

按「离『用户觉得值』的距离」排序，从近到远：

| 档 | 指标 | 为什么更接近真实价值 | 采集成本 |
|---|---|---|---|
| **最接近** | **出行后回访：用户是否真的去了推荐的地方**（打卡/轨迹/复述） | 唯一能证明「推荐被采纳」的**行为**证据，不是意向 | 高（要跟踪到线下） |
| **次接近** | **目的地级转化**（点开→加进行程→保存/分享→导出） | 这是「采纳」的漏斗，比点击深一层 | 低 |
| **次接近** | **回访率 / 复访**（同一用户短期内再来问第二个城市/下一次旅行） | 旅游天然低频（一周两次），**回访是稀缺信号**，一旦有就很硬 | 低 |
| **中** | **会话级满意度问询**（结束后 1 题：「这次的推荐你会真的照着去吗？」） | 直接问，但只有意向 | 低 |
| **弱** | 停留时长 / 滚动深度 | **长停留可以是"没看懂"或"在找别的东西"**，不单调 | 低 |
| **最弱** | CTR | 只能测「有没有被吸引点」，测不到「去了值不值」 | 最低 |

**特别提醒（旅游领域独有）：CTR 在本领域是特别不可靠的代理，因为「点击」和「去」之间有一整个履约链**（订票、请假、天气、同行人）。多家竞品实测的共同失败模式就是「生成得很好看，然后用户打开别的 App 去订票」（见 `ai-travel-competitive-landscape.md` §0）。**点击率高的「网红清单」往往不是「值得去」的清单。**

### 2.2 长期 vs 短期冲突：怎么处理（有明确工业做法）

**这不是理论问题，有据可查的工业结论如下：**

1. **YouTube 明确把排序目标从「点击概率」改成「每次曝光的期望观看时长」**，理由写在论文里：*"Ranking by click-through rate often promotes deceptive videos that the user does not complete ('clickbait') whereas watch time better captures engagement"* [一手，Covington et al., RecSys'15, Deep Neural Networks for YouTube Recommendations, §4]。
   → **方法论：当 CTR 与「后续深度行为」冲突时，以深度行为为优化目标，CTR 只作为健康度护栏。** 这个原则直接可移植：**旅游场景里的「深度行为」= 加进行程 / 保存 / 实际出行。**

2. **Booking.com 的「代理过度优化（Proxy Over-optimization）」实录**——比 CTR 陷阱更贴本项目：他们以 CTR 为代理去优化转化率，结果模型学会了**推荐"和用户正在看的酒店极度相似"的酒店来骗点击**，用户被淹没在相似酒店里，**最终反而伤害了转化率** [一手，KDD'19 §3]。他们给出的对策是：*"Offline model performance metrics are only a health check... focus on a fast cycle of developing hypotheses, building minimum models to test them in experiments."*
   → **对本项目的直接映射：如果拿「点击/点赞/沉浸时长」当优化目标，系统会学会推「看着像你想去的」，而不是「你真觉得值的」。** 这恰好是你描述的「看起来契合期待」问题在算法层的机制。

3. **具体的实验设计原则（工业实践）**：
   - **只对模型有分歧的用户做分析**（triggered analysis）——Booking 提到，当两个模型高度一致时，全量 A/B 的差异会被稀释到测不出来；只统计「被分到不同体验」的用户，能显著提高灵敏度 [一手，KDD'19 §7.4]。
   - **长期指标看的是「保留/复访」，短期看「转化」**——两者冲突时（短期涨、长期跌），把这当作**红旗**而非胜利。旅游场景里长期指标极稀疏（一年 1-2 次旅行），单次 A/B 无法测长期 → **解法不是把 A/B 拉长到一年，而是用「代理指标的因果链」**：先证明「加进行程」与「实际出行」相关，再优化可短期测的前者。这一步**必须自己验证相关性**，不能假设。

### 2.3 著名的「CTR 陷阱」案例清单（按本项目相关度排序）

| 案例 | 内容 | 证据级 |
|---|---|---|
| YouTube clickbait | CTR 优化 → 标题党视频被推送、用户点完就走；改为期望观看时长 | **一手**（RecSys'15 原文，见上） |
| 学术系统性论证 | "Clicks can be Cheating: Counterfactual Recommendation for Mitigating Clickbait Issue"（Wang et al., CIKM'21）：*点击与满意度之间存在显著鸿沟*，在 CTR 数据上训练的模型会把"欺骗性标题"越推越多 | **一手**（arXiv:2009.09945 摘要） |
| Booking.com 相似酒店陷阱 | 用 CTR 当转化率代理 → 推极相似酒店骗点击 → 选择悖论 → 转化率受损 | **一手**（KDD'19 §3） |
| 长期/短期多目标 | "Multi-Task Fusion via RL for Long-Term User Satisfaction"（arXiv:2208.04560）：单点 CTR 指标与长期满意度不一致，工业上已转向多目标融合 | **二手**（摘要级，未读全文） |

## 3. 「满意度」怎么量化

### 3.1 行为指标：各自测的是什么（别混用）

| 指标 | 真实含义 | 在旅游场景的可用性 |
|---|---|---|
| **Dwelling time 停留时长** | 投入程度的**弱**代理；可以是"读得入迷"，也可以是"在找出口" | 低——本项目是对话式，停留时长混进了打字思考时间 |
| **Return rate 回访率** | **最强的隐式信号**，但旅游品类结构性地低（一年 1-2 次） | 中——要按「同一用户是否来问第二次/第二个目的地」定义，别用 DAU 式口径 |
| **Explicit rating 显式打分** | 意向/态度，且**有严重的选择偏差**（见 §3.2） | 低，除非设计成「一行代价极低」的打分 |
| **Post-consumption satisfaction 消费后满意度** | **最接近「值不值」**——但要落到线下（去了之后回来评） | **最高价值、最难采集**；这是本项目最该设计但最难的一环 |

**核心判断：`[推论]` 对本项目而言，「消费后满意度」是唯一真正对应目标函数的指标——因为你的成功定义（用户去了之后觉得值得）发生在产品边界之外。** 任何站内指标都只是它的代理，而**代理与目标之间的相关性必须自己验证**，不能引用来假设。

### 3.2 ⚠️ 为什么不能用平均星级当满意度

`[一手]` Hu, Zhang & Pavlou, *Overcoming the J-Shaped Distribution of Product Reviews*, CACM 2009：

- 实测 Amazon 2005 年 2-7 月数据：**书 78%、DVD 73%、视频 72% 的评分 ≥ 4 星**，分布呈 **J 型**（大量 5 星 + 一些 1 星 + 中间几乎没有）。
- 归因于两个**自选择偏差**：**购买偏差**（只有高估值的人才会买）+ **漏报偏差**（只有极端满意/不满意的人才有动力写）。
- 对照实验（所有人评同一张 CD）得到的是**单峰分布**，均值显著低于 Amazon 上的均值。
- **结论：均值只有在单峰或对称双峰分布下才是有效估计；J 型下均值是产品质量的劣质代理。**
- 他们提出的无偏估计器要同时纳入：**均值 + 标准差（分歧度）+ 两个众数（克服漏报）+ 价格（克服购买偏差）**。

**对本项目的直接推论（重要）：**
1. **景区的平均评分同样受"只有去过的人才评 + 只有极端体验才评"双重偏差。** 一个 4.5 分的景区，可能是「大家去了都觉得还行」，更可能是「觉得一般的人懒得评，觉得好的人来刷」。**这两个世界的均值一样，但用户去之后的体验完全不同。**
2. **「评分高 → 相关性高」这个映射是错的**；应当改成判据：
   - **评分分布的形状**（全 5 星的 4.8 分 vs 双峰的 4.5 分，后者更值得警惕）；
   - **评价量与评价者的多样性**（只有几百条 vs 数万条）；
   - **负面评价的内容**（J 型的 1 星那一簇在抱怨什么——排队？票价？景色其实一般？**抱怨的具体内容才是"值不值"的真实信息**）。
3. **不要用均值做 NDCG 的 rel 标签**。rel 应由**专家/规则按"值得去"分级**产出（§5.3），均值只作为其中一个输入信号。

### 3.3 「推荐意愿」类指标要谨慎用（NPS 的反证）

`[一手]` Morgan & Rego, *The Value of Different Customer Satisfaction and Loyalty Metrics in Predicting Business Performance*, Marketing Science 2008（ACSI 1994-2000 数据）：

- **平均满意度分值**对后续业务表现的预测力最强；**Top-2-Box** 次之；
- **基于推荐意愿（net promoters）和推荐行为的指标，几乎没有预测力**；
- 原文明确说：主张「客户反馈体系应只关注推荐意愿」的建议是 **misguided**。

→ **对本项目：别把「你会推荐给朋友吗」当核心指标。** 如果一定要用，把「**平均满意度 + Top-2-Box**」作为主指标更可靠。这条对旅游尤其相关——旅游产品普遍爱用 NPS，而证据说它的预测力弱。

## 4. 商业/电商领域：怎么评估「买完了不后悔」

### 4.1 电商端的成熟做法（可借用）

| 做法 | 机制 | 借用方式 |
|---|---|---|
| **退货率 / 取消率当质量指标** | 推荐了但退货率高 = 推荐「不合身/与描述不符」 | **旅游的对应物：改签率、退改率、行程被丢弃率、去了之后回来给差评/删行程** |
| **客单价 + 复购 + 评价的组合** | 单一指标会被钻空子，组合使用 | 组合「采纳率 × 后续行为 × 显式反馈」 |
| **个性化推荐与退货的关系（有研究，证据方向需注意）** | 有研究（Korganbekova et al., 工作论文, Wharton）报告：**个性化组的退货率比对照组低 10%**，解释为「匹配更好」 | `[二手]` 工作论文，未同行评审；**方向是"个性化降低退货"，不是"个性化提高退货"**。见下方反例说明 |

**⚠️ 常见流传的「推荐导致高退货率」说法，我没能找到可引用的同行评审证据。** 我在调研中看到的方向反而是「个性化降低退货」。**所以不要把「推荐→退货率高」当作既成事实来论证**，那会是一个证据不支持的强断言。真正有据的电商教训是下面的「指标选错」。

### 4.2 电商的真实反例教训（有据）

1. **CTR 代理 → 转化率受损**（Booking，§2.2）——这是最直接、最可引的一条。
2. **评分的 J 型偏差**（§3.2）——把星级当满意度就必然失真。
3. **「好的离线指标 ≠ 好的业务结果」**（Booking KDD'19 的 23 组 RCT 对比，r = −0.1）——工业界最硬的一条反直觉证据。

### 4.3 旅游场景该建的「不后悔」指标（`[推论]`，我的建议，未验证）

- **采纳后后悔率**：用户把 X 加进行程，之后又移除了 X 的比例；
- **改单次数**：同一行程里对同一天的推荐反复替换 = 犹豫/不满意；
- **「去了报告」回收率**：行程结束后回来反馈（哪怕是 1 题「去过的这几个值不值」）；
- **再推荐接受率**：同一用户第二次提问时，是否接受同类推荐（信任保留）。

**这四条都不需要真实线下数据即可上线，且能直接对应"用户觉得值"**——比任何 CTR 变体都更贴近你的目标函数。

## 5. 冷启动与无历史数据时：靠什么判断推荐质量

**这一节是本报告对当前项目最直接有用的部分。**

### 5.1 第一步不是评估推荐，是评估「输入数据塌缩到什么程度」

在没有任何用户行为之前，**先量「特征有没有个性」，这是纯统计、不需要任何标注**：

| 指标 | 怎么算 | 判据 |
|---|---|---|
| **等级字段的方差 / 分布熵** | 对候选池统计 `等级` 的取值分布 | 若 5A/4A 占了 90%+，**这个特征在 40% 权重下等价于常数偏置** |
| **等级与「个性化字段」的相关性** | 等级 vs 主题/季节/人群适配度 的互信息 | 高度相关 = 等级在"偷"个性化信号的解释力，权重会被它吃掉 |
| **Top-K 重合度（跨用户）** | 对 N 个不同画像的模拟用户各推 5 个，算两两 Jaccard | **这是最直接诊断"推荐塌缩"的指标**：Jaccard 接近 1 = 不管什么用户推荐都一样 |
| **主题/类别覆盖率** | top-5 里出现的不重复类别数 / 类别总数 | 覆盖率极低 = 多样性不足，用户"去了觉得跟别处一样" |

**`[推论]` 我怀疑现系统的真实病根就是 Top-K 重合度极高**：因为 40% 权重压在一个无方差字段上，剩余 60% 的个性化信号不足以把推荐拉开。**这个假设可以用合成画像直接测出来，不需要任何真实用户数据——建议作为第一个动作。**

### 5.2 第二步：无行为数据时，可用的评估手段（按证据强度排序）

| 手段 | 说明 | 证据强度 | 注意 |
|---|---|---|---|
| **专家分级标注 + 一致性校验** | 请 2-3 个熟悉当地的人对候选独立标「必去/值得/顺路/别去」 | **最强**（这是黄金标准） | 必须报 **Cohen's κ / Fleiss' κ**，不是简单一致率。κ<0.4 说明「这个任务本身没有稳定答案」，此时任何指标都没意义 |
| **成对比较（Bradley-Terry）** | 「A 和 B 只能去一个，去哪个」 | 强 | 比绝对打分稳定得多；`[推论]` 绝对星级评分在本项目里已被证明不可靠（§3.2） |
| **LLM 当裁判（LLM-as-judge）** | 用 LLM 按 rubric 打分 | **中，且必须校准** | 见 §5.3 |
| **规则/约束校验** | 距离、开放时间、季节、体力强度是否物理可行 | 强（但只管"错不错"，不管"值不值"） | 竞品实测的失败大多在这一层（高德 18:00 推 16:30 关门的动物园）——**这层不做，上层评分再好都白搭** |
| **公开数据回测** | 用已有 OTA 榜单/游记里的"实际去了"当弱标签 | 中 | **注意选择偏差**：游记作者本身就是高估值人群（§3.2 的购买偏差） |

### 5.3 LLM-as-judge 的正确用法：先校准，再使用

这是本项目最可能落地、也最容易做错的一环。

**正确流程（不是"让 LLM 打分"）：**
1. **人工标一小批（如 100-200 对）**作为金标；
2. **让 LLM 裁判在同一批上跑**；
3. **算一致性（κ，不是一致率）**；
4. **只有在 κ 达到可接受水平（经验上 κ ≥ 0.6，即 substantial）后，LLM 才可替代人工去扩大规模**；
5. **定期用新的人工样本重校**——裁判会漂移（模型升级、prompt 改动都会）。
6. **必须用 rubric 而不是整体印象打分**。`[二手]` 有分析指出：**同一批判定结果，因裁判设计/prompt/边界约定的细节不同，算出的 κ 可以差很多**（arXiv:2606.00093 "Agreement Metrics for LLM-as-Judge Evaluation"，摘要级）。

**`[二手]` 关于"少量非专家标注是否够用"**：Snow et al. 的经典结论是**任务简单时，少量非专家标注的平均可接近专家**；这与"必须请专家"并不矛盾——**关键在任务复杂度**。「这个景区值不值得去」高度依赖本地知识，属复杂任务 → **别指望众包平均能替代本地专家**。

### 5.4 冷启动的实操建议（`[推论]`，按性价比排序）

1. **建 100-200 条人工分级标注集**（覆盖 3-5 个城市、多个主题），作为**唯一的黄金基准**，永不与自动标注混用；
2. **用它校准 LLM 裁判 → 扩大标注到全库**，报 κ；
3. **在标注集上把「景区等级」这个特征做消融实验**：去掉 40% 权重后 NDCG 变化多少。**如果掉得很少甚至上升，就证明"等级塌缩"确实是伪信号**——这是能直接改变产品决策的一次实验；
4. **同时报「跨用户 Top-K 重合度」与 NDCG**：只看 NDCG 会奖励"给所有人都推同一个经典清单"，而这个清单正因为"对所有人都还行"而得分高——**这又是一个「平均值陷阱」**；
5. **在上线前用物理约束校验（距离/时间/开放/季节）做一次全量硬过滤**，这层的失败率应单独报，不与相关性指标混算。

## 6. 给本项目的最小可行评估方案（一页纸）

```
第一层：物理可行性（硬过滤，必须 100% 通过）
  距离/通勤时间、开放时间、季节、体力强度、同行人约束
  指标：违规率 = 0（任一 >0 即不可上线）

第二层：排序质量（专家分级标注集上）
  主指标：NDCG@5（linear gain，rel∈{0,1,2,3}，IDCG 定义固定写死）
  辅指标：top-3 必去档命中率、成对比较准确率
  弃用：Precision@5、MRR、RMSE（小 K 下无区分度，见 §1.3 实测）

第三层：多样性/塌缩诊断（无需行为数据）
  跨画像 Top-5 Jaccard 重合度、top-5 主题覆盖数、等级字段方差
  目的：证明推荐不是"对所有人都推同一份 5A 清单"

第四层：在线（有流量后）
  短期：加进行程率、保存率
  长期：回访率（同用户第二次提问）、采纳后后悔率（加进又移除）
  护栏：CTR 只做异常检测，不做优化目标（YouTube/Booking 的教训）
```

## 8. 我没能确认的事（诚实清单）

1. **旅游荐品的行业基准**（如"旅游推荐 NDCG@5 多少算好"）——**没有公认基准**。不同候选池、不同标注口径下数值不可比。**本项目应自建基线，而不是对标外部数字。**
2. **「推荐导致高退货率」的同行评审实证**——**没找到**。只找到方向相反的工作论文。所以本报告不把它写成结论。
3. **「消费后满意度」与「站内采纳指标」的相关性**——理论上是核心链条，但我**没找到可引用的实证**。这是本项目上线后**必须自己验证**的第一件事，不能引用假设。
4. **α-NDCG / N-NDCG 的标准实现细节**——各家对"首个命中是否折扣"约定不一，我的探针已实测出这种差异会导致方向性错误（§1.4）。**别自实现。**
