# 信息组织系统与标签系统

**Where to Travel v0.4** · 本文描述产品的信息架构与标签体系。

---

## 一、总览

产品有三层信息结构，**每层用不同的组织方式**：

```
┌─────────────────────────────────────────────────────────┐
│  ① 交互层  ── 页面分区            按「操作阶段」分区       │
├─────────────────────────────────────────────────────────┤
│  ② 语义层  ── 标签体系            按「用户意图」打标签     │
├─────────────────────────────────────────────────────────┤
│  ③ 数据层  ── 表结构              按「实体关系」建模       │
└─────────────────────────────────────────────────────────┘
```

**核心原则：目的用路径，意义用标签。**

- **路径**（目录/分区）表达**唯一的流程位置** —— 如「左栏对话 / 右栏结果」是操作目的
- **标签**（多值枚举）表达**多元的意义** —— 如一个景区可同时是「自然类」「低人流」「免费」

**分区依据：用户的操作阶段**，不是信息类型。

| 区 | 回答的问题 | 变化时机 |
|---|---|---|
| 左栏对话 | 「我在跟它说什么」 | 每轮 |

## 三、② 语义层：标签体系

### 3.1 主标签体系：动机七类

**这是整个产品最核心的标签** —— 所有推荐逻辑都挂在它下面。

```
动机（单值，互斥）          ← 决定「怎么排」
├── 恢复/逃离   低强度 · 自然 · 人少 · 慢节奏
├── 连接/关系   交通便利 · 老少皆宜
├── 探索/新奇   小众 · 非典型
├── 表达/展示   视觉冲击 · 出片率高
├── 成就/完成   5A 标志性 · 打卡优先
├── 文化/沉浸   历史文化属性 · 博物馆/遗址
└── 美食/感官   餐饮驱动
```

**主标签只有一个**（`primary`），**次标签最多两个**（`secondary`）。

### 3.2 标签的三层映射

```
用户那句话
    │  ① 语义识别（LLM）
    ▼
动机标签          「恢复/逃离」
    │  ② 规则映射（写死在 MOTIVATION_RULES）
    ▼
偏好标签          prefer_nature=0.45 / crowd_penalty=0.5 / avoid_serious=0.5
    │  ③ 打分应用
    ▼
景区排序          自然类 +0.45 · 拥挤 -0.5 · 严肃场所 -0.5
```

**映射表（`MOTIVATION_RULES`）是产品调优的主要抓手** —— 改权重就能改推荐效果，不用动模型。

| 动机 | 主要偏好标签（权重） |
|---|---|
| 恢复/逃离 | `prefer_nature` +0.45 / `crowd_penalty` -0.5 / `avoid_serious` -0.5 / `avoid_indoor` -0.25 |
| 连接/关系 | `prefer_easy_transport` +0.4 / `prefer_level_high` +0.2 |
| 探索/新奇 | `prefer_level_low` +0.3 / `prefer_less_crowd` +0.3 / `prefer_level_high` **-0.15** |
| 表达/展示 | `prefer_level_high` +0.3 / `prefer_photo_hint` +0.3 |
| 成就/完成 | `prefer_level_high` +0.4 / `prefer_free` -0.05 |
| 文化/沉浸 | `prefer_level_high` +0.2 / `prefer_culture_hint` +0.35 |
| 美食/感官 | `prefer_culture_hint` +0.15 / `prefer_level_low` +0.1 |

> ⚠️ **注意「探索/新奇」的 `prefer_level_high` 是负权重** —— 同一个标签在不同动机下方向相反。
> 这是标签必须**挂在动机下**而不能全局定义的原因。

### 3.3 画像标签（结构化字段）

| 字段 | 类型 | 是否多值 | 证据校验 |
|---|---|---|---|
| `destination` | 城市名 | 单值 | ✅ 需用户提及 |
| `origin` | 城市名 | 单值 | ✅ |
| `primary` | 动机七类之一 | 单值 | ✅ |
| `primary_intensity` | 1-5 整数 | 单值 | — |
| `secondary` | 动机七类 | **多值 ≤2** | ✅ |
| `hours` | 1-12 整数 | 单值 | ✅ |
| `companions` | 独自/情侣/父母/朋友/带娃 | 单值 | ✅ |
| `pace` | 紧凑/适中/松散 | 单值 | ✅ |
| `interests` | 自由文本 | **多值** | ✅ |
| `avoid` | 自由文本 | **多值** | ✅ |
| `must_see` | 自由文本 | **多值** | ✅ |
| `summary` | 自然语言 | 单值 | — |

**三类特殊标记（不进对外画像）：**

| 字段 | 用途 |
|---|---|
| `_turns` | 轮数，供 `ready` 判据 |
| `_extract_error` | 抽取失败原因（调试用） |
| `xxx_remove` | 列表删除指令（**不是存储字段**，是操作指令） |

**列表字段支持增删**，靠 `xxx_remove` 机制：

```
"avoid": ["爬山"]                      → 追加
"avoid_remove": ["爬山"]               → 删除（用户说「其实我不介意爬山」）
```

### 3.4 数据侧标签（景区属性）

| 标签 | 来源 | 取值 |
|---|---|---|
| `level` | 官方 | 5A / 4A / 3A / 2A / 1A |
| `district` | 官方 | 北京 16 区 |
| `ticket_free` | 官方 | 0 / 1 |
| `price_high` / `price_low` | 官方 | 数值 |
| `saturation` | 官方实时 | 0-100（拥挤度） |
| `metro` / `bus` / `highway` | 官方 | 交通可达性文本 |
| `lon` / `lat` | 高德 | 坐标 |
| `embedding` | 百炼 | 1024 维向量 |

**派生标签（代码算，不存库）**

场所气质由 `_kind(name)` 从名称推断，返回 **3 个集合标签**：

| 集合标签 | 线索词（`xxx_HINTS`） |
|---|---|
| `serious` | 纪念馆 · 烈士 · 抗战 · 革命 · 党史 · 军事 · 国防 · 警示 · 法制 · 禁毒 · 消防 · 安全 |
| `indoor` | 博物 · 馆 · 展 · 厅 · 中心 |
| `nature` | 公园 · 湿地 · 森林 · 湖 · 山 · 谷 · 峪 · 溪 · 植物园 · 花园 · 景区 · 绿道 · 郊野 |

另有 **4 组独立的线索词表**，供不同动机打分时直接匹配名称：

| 线索表 | 线索词 | 用于 |
|---|---|---|
| `PHOTO_HINTS` | 景 · 公园 · 街 · 桥 · 塔 · 长城 · 湖 · 山 · 园 | 表达/展示 |
| `CULTURE_HINTS` | 博物 · 遗址 · 故居 · 寺 · 庙 · 文化 · 纪念馆 · 故宫 · 坛 · 陵 · 馆 · 堂 | 文化/沉浸 · 美食/感官 |

**交通可达性是字段判据，不是线索词：** `metro` 非空 → `prefer_easy_transport` 生效。

> ⚠️ **平台数据没有「场所类型」字段**，所以只能靠**命名特征推断**。
> 这是已知的粗糙点 —— 名字里没有线索词的景区会漏判。

## 五、三层如何咬合

```
用户说「最近太累，想找个人少安静的地方待一天」
   │
   │ ① 交互层：POST /api/chat  { text, session_id }
   ▼
   │ ② 语义层：LLM 抽取
   │      primary = "恢复/逃离"
   │      hours   = 8
   │      avoid   = ["人多"]
   ▼
   │ ③ 语义层：规则映射
   │      crowd_penalty = 0.5, prefer_nature = 0.45, avoid_serious = 0.5
   ▼
   │ ④ 数据层：SQL 取候选 + 打分排序
   │      SELECT * FROM attractions
   │      LEFT JOIN crowd_index USING(name)
   ▼
   │ ⑤ 数据层：编排（聚类 → TSP → 时间剪枝）
   ▼
   │ ⑥ 交互层：右栏渲染
   │      #narrative  #timeline  #map
   ▼
   用户看到行程
```

**关键：中间任何一层出问题，表现都在最外层。**

| 症状 | 实际出问题的层 |
|---|---|
| 「未知还查不了」 | ② 语义层（占位词未清洗） |
| 「嗯，能再多说说吗」 | ② 语义层（兜底不读输入） |
| 8 小时排成 14 小时 | ⑤ 数据层（时间预算未剪枝） |
| 推荐了纪念馆 | ③ 语义层（`avoid_serious` 未生效） |

## 六、设计取舍

### 为什么动机是「单值主 + 多值次」

**单值**：一次出行的核心意图是唯一的 —— 说「想放松」和「想打卡」是两件事，硬合并会两头不讨好。

**多值次**：人总有次要诉求（「主要想放松，顺便吃点好的」），但不能喧宾夺主。

### 为什么不用文件夹装标签

景区**没有目录层级** —— 一个景区可以同时是「5A + 朝阳区 + 免费 + 自然类 + 低人流」。

**用目录 = 只能选一个父级**，其余属性无处安放。**所以全部用标签（多值字段），只在需要「唯一归属」的地方用外键。**

### 为什么 `events.user_id` 是 NOT NULL

**这是把隐私政策变成结构约束**：

> 「匿名不落库」如果只写在文档里，某天有人写代码时忘了判空就会破。
> 设成 `NOT NULL`，**匿名事件在物理上写不进去**。

**双层保障（都实测过）：**

| 层 | 机制 | 实测结果 |
|---|---|---|
| 代码层 | `analytics.track()` 里 `if not user_id: return` | 匿名调用 → 落库 0 条 ✓ |
| 数据库层 | `user_id TEXT NOT NULL` | 写 NULL → `NOT NULL constraint failed` ✓ |

**迁移方式**：SQLite 不支持 `ALTER COLUMN`，需重建表（`CREATE new → INSERT SELECT → DROP → RENAME`）。
迁移前会检查有无空值行；**有空值则跳过并留痕，不擅自删数据**。
