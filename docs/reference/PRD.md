# Where to Travel 产品需求文档（PRD）
**产品名称：** Where to Travel
**版本：** V1.2 课程作业版
**平台：** Web（移动端适配）
**覆盖范围：** 全国（北京为真实数据源，其他省份为占位数据）
**数据策略：** 北京真实 API/公开数据 + 其他省份结构化占位数据

## 一、产品概述

### 1.1 产品定位
Where to Travel 是一个以 AI 对话为核心入口，聚合文旅官方与多平台信息，通过需求本质挖掘实现个性化推荐，并提供可解释推荐与旅程预演的旅游决策平台。

**全国覆盖策略：**

- 产品架构支持全国范围，用户可查询任意省份。
- **北京**作为真实数据验证城市，接入真实 API 与公开数据，用于证明核心逻辑可行。
- **其他省份**使用结构化占位数据，用于演示全国扩展能力，所有占位数据明确标注“演示数据”，不声称真实。

一句话：**不只告诉你“去哪”，先帮你搞清楚“为什么去”，再告诉你“去了会遇到什么”。**

### 1.2 核心价值主张
**面向游客（C端）：**

- 通过 Travel for What 动机挖掘，识别旅行本质需求，而非标签匹配。
- 聚合文旅官方、内容平台、地图、天气等多源数据，提供可交叉验证的推荐。
- 每条推荐附带来源与置信度，结合用户历史行为动态调整。
- 提供基于真实/占位数据的轻量级旅程预演，让用户决策前看到“这一天会怎么过”。

**面向文旅局（B端）：**

- 官方认证入驻，发布推荐内容与活动信息。
- 查看内容曝光、点击、用户互动等数据看板。
- 不做复杂业务系统，票务预约等由官方官网承担。

### 1.3 核心差异化

| 维度 | 大众点评 | 小红书 | Where to Travel |
| --- | --- | --- | --- |
| 核心逻辑 | 评价驱动 | 内容种草 | 动机驱动 + 多源交叉验证 |
| 推荐粒度 | 单点商户 | 单篇笔记 | 个性化行程 + 预演 |
| 个性化 | 基于历史行为 | 基于内容偏好 | 基于旅行价值观 + 本次动机 |
| 可解释性 | 评分展示 | 弱 | 多源来源 + 置信度 + 行为反馈 |
| 官方联动 | 商户入驻 | 品牌号 | 文旅局认证 + 内容发布 + 数据看板 |
| 数据策略 | 全量真实 | 全量真实 | 北京真实 + 其他占位，分层标注 |

### 1.4 不做的范围（课程作业限定）

- 不做支付、票务、退款等交易闭环。
- 不做完整评价社区（仅做景点级评分）。
- 不做真实文旅局付费合作与结算。
- 不做 3D 全景/VR/直播等重型云游。
- 不做其他省份的真实数据接入，仅用占位数据演示。
- **本版本暂不实现 Travelling 事件自动生成与游记事件提炼，相关规划见“下一步计划”。**

## 三、核心功能模块

### 3.1 C端功能

#### 模块一：AI 对话助手（核心入口）
**功能描述：** 用户通过自然语言与 AI 对话，系统逐步收集需求信息，最终生成个性化行程推荐。

**对话流程：**

text
```
用户进入 → 基础画像（首次）
         → Travel means What（长期价值观，首次）
         → Travel for What（本次动机）
         → 本次需求（时间/预算/目的地）
         → 偏好深挖（动态追问）
         → AI 生成 2-3 条候选行程
         → 用户选择一条 → 旅程预演
         → 用户反馈调整 → 最终行程
         → 行后反馈 → 更新用户模型
```
**基础画像采集（首次使用）：**

- 出行同伴类型（独自/情侣/家庭带娃/朋友结伴/带父母）
- 年龄段
- 常住城市
- 是否有目标城市出行经验

**Travel means What（长期价值观，首次使用，轻量 2-3 题）：**

用投射式选择采集：

- 如果旅行是一件事，它更像：给自己充电 / 和重要的人创造回忆 / 去看看没见过的世界 / 完成心愿清单 / 拍出值得分享的内容 / 暂时离开日常
- 旅行回来，你最希望得到什么：精力恢复 / 关系更近 / 眼界变宽 / 成就感 / 好照片 / 一段安静回忆

输出：旅行意义画像（主标签 + 次标签），存入用户模型长期使用。

**Travel for What（本次动机挖掘，每次旅行触发，不超过 3 轮对话）：**

核心动机分类（可多选，需排序）：

| 动机类型 | 推荐策略倾向 |
| --- | --- |
| 恢复/逃离 | 低强度、自然、人少、慢节奏 |
| 连接/关系 | 互动性强、老少皆宜、节奏宽松 |
| 探索/新奇 | 小众、新开、非典型景点 |
| 表达/展示 | 出片率高、视觉冲击强、网红机位 |
| 成就/完成 | 标志性景点、打卡式、效率优先 |
| 文化/沉浸 | 深度讲解、在地体验、非游客区 |
| 美食/感官 | 餐饮驱动、市场、街巷、老字号 |
交互方式：投射式问题 + 对比选择 + 场景回忆 + 反向问题。

输出：本次旅行动机画像，可视化展示给用户确认或修正。

**偏好深挖（AI 动态追问）：**

- 对景点的评价维度排序：性价比、人少、文化深度、交通便利、拍照好看
- 体力接受度：暴走型/休闲型
- 已去过或明确不想去的地方
- 让用户描述“上一次最满意的旅行”，AI 从中提取偏好标签

**AI 对话技术方案：**

- 模型：GLM-4 Flash（免费，128K 上下文）
- 意图解析：将用户输入解析为结构化查询条件
- RAG 检索：从向量知识库中检索候选景点与攻略
- 动态追问：根据已采集信息判断缺失维度，生成追问
- 数据源感知：根据用户目的地自动切换真实/占位数据，并在回答中标注

#### 模块二：智能推荐引擎
**推荐排序公式：**

text
```
score = 动机匹配度 × 0.35
      + 多源评价一致性 × 0.20
      + 用户画像匹配度 × 0.15
      + 官方推荐权重 × 0.10
      + 新鲜度 × 0.10
      - 拥挤度 × 0.10
```
**动机-推荐映射规则：**

| 动机 | 权重调整 |
| --- | --- |
| 恢复/逃离 | 自然类 +0.3，人流密度 -0.3，行程密度 -0.2 |
| 连接/关系 | 互动体验 +0.25，交通便利 +0.2，老少皆宜 +0.2 |
| 探索/新奇 | 小众标签 +0.3，热度 -0.15，新开景点 +0.2 |
| 表达/展示 | 出片率 +0.3，视觉冲击 +0.2，网红机位 +0.2 |
| 成就/完成 | 标志性 +0.3，效率 +0.2，经典路线 +0.2 |
| 文化/沉浸 | 深度讲解 +0.3，在地体验 +0.25，非游客区 +0.2 |
| 美食/感官 | 餐饮密度 +0.3，老字号 +0.2，市场街巷 +0.2 |
**数据源分层处理：**

- 北京：使用真实数据计算完整评分。
- 其他省份：使用占位数据计算评分，但置信度强制标注为“低（占位数据）”，并在推荐理由中提示“该地区为演示数据，建议参考真实平台”。

#### 模块三：可解释推荐
每条推荐附带三层信息：

**第一层：推荐理由（自然语言）**

> “推荐故宫，因为：①你本次旅行动机为文化沉浸（强度 4/5）②你偏好文化历史类景点 ③本周官方有特展 ④近 30 天好评率 87%。”
>
>
**第二层：数据来源与交叉验证**

| 信息类型 | 北京来源 | 其他省份来源 | 示例 |
| --- | --- | --- | --- |
| 官方数据 | 北京市公共数据开放平台 | 占位数据 | 景区等级、开放时间 |
| 实时人流 | VisitBeijing MCP | 占位数据 | 当前游客数量与密度 |
| 用户评价 | 聚合大众点评/小红书 | 占位数据 | 评分 4.7/5（1.2 万条） |
| 地理信息 | 高德/百度地图 API | 高德/百度地图 API（真实） | 距离、交通耗时 |
| 天气 | 和风天气 API | 和风天气 API（真实） | 当日天气、温度 |
**第三层：置信度标注**

- **高**：多源真实数据一致，用户画像完整（仅北京可能达到）。
- **中**：数据源存在分歧，或画像不够完整。
- **低**：冷启动阶段、数据不足，或使用占位数据（其他省份默认低置信度）。

**结合用户行为数据的交叉验证：**

> “你上次选择了 XX 景点，系统推荐理由是‘人少安静’，但你的行后评价是‘太冷清了’，本次已降低同类景点的推荐权重。”
>
>

#### 模块四：旅程预演（轻量云游）
**定位：** 基于真实/占位数据的决策预演，不是虚拟旅游。

**功能描述：** 用户选定候选行程后，系统生成文本时间线 + 地图路线，展示“如果这么走，会遇到什么”。

**输出示例（北京真实数据）：**

| 时间 | 地点 | 交通 | 预计耗时 | 天气/人流 | 会遇到什么 | 风险 | 备选 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 09:30 | 奥森公园南园 | 地铁 8 号线 | 1.5h | 晴，人流低 | 晨练的人、湖边安静 | 风大 | 地坛公园 |
| 11:30 | 胡同咖啡馆 | 打车 15min | 1h | 人流中 | 安静、有座位 | 可能满座 | 备选咖啡馆 |
| 13:00 | 老字号午饭 | 步行 8min | 1h | 排队约 10min | 本地口味 | 口味偏重 | 附近面馆 |
**AI 总结：** “这条路线整体强度低，适合想放松、不想赶路的你。最大风险是午饭排队和下午晒，已给备选。置信度：中高。”

**数据来源标注：** 每条预演信息标注来源，不能确定的事情标注“推测”。其他省份预演会明确标注“演示数据”。

#### 模块五：信息聚合与浏览
**功能描述：** 除 AI 对话外，提供筛选浏览的信息流入口。

**聚合内容来源：**

- 北京：北京市文旅局官方发布、北京旅游网 MCP、小红书/大众点评外链、地图 API、天气 API。
- 其他省份：占位官方发布、占位景点信息、地图 API（真实）、天气 API（真实）。

**筛选维度：** 省份/城市、景点类型、主题标签、距离、热度、官方推荐、评分。

**用户评分：** 本平台支持用户对景点进行评分（1-5 分），作为多源评价的组成部分。其他省份占位景点也可评分，但标注“演示”。

#### 模块六：用户画像与决策闭环
**用户画像模型：**

| 维度 | 字段 | 采集方式 |
| --- | --- | --- |
| 人口统计 | 年龄段、常住城市、同伴类型 | 首次对话 |
| 旅行价值观 | 旅行意义画像（主+次标签） | Travel means What |
| 本次动机 | 动机画像（多维强度） | Travel for What |
| 兴趣偏好 | 文化/美食/自然/拍照/购物 | 对话+行为 |
| 消费偏好 | 预算区间、性价比敏感度 | 对话 |
| 行为习惯 | 体力接受度、行程密度偏好 | 对话+反馈 |
| 历史决策 | 去过的地方、满意/不满意、推荐 vs 实际偏差 | 行后反馈闭环 |
**冷启动策略：** 新用户通过对话式追问逐步探索潜在需求，先给宽泛推荐，根据反馈快速收敛。

**行后反馈闭环：**

- 实际去了哪些景点
- 哪个推荐符合预期、哪个不符合
- 满意度评分（1-5 分）
- 回写动机画像与偏好模型

## 四、数据源与聚合策略

### 4.1 数据分层策略

| 层级 | 覆盖范围 | 数据性质 | 用途 | 置信度 |
| --- | --- | --- | --- | --- |
| L1 | 北京 | 真实 API/公开数据 | 验证核心逻辑，完整功能演示 | 高/中 |
| L2 | 其他省份 | 结构化占位数据 | 演示全国扩展能力，功能占位 | 低（标注演示） |
| L3 | 全国通用 | 地图 API、天气 API | 交通、天气等通用信息 | 高 |

### 4.2 北京真实数据源清单

| 数据类型 | 来源 | 获取方式 | 更新频率 |
| --- | --- | --- | --- |
| 景区名录 | 北京市公共数据开放平台 | API（CSV/XLSX/RDF） | 定期更新 |
| 旅行社信息 | 北京市公共数据开放平台 | API | 定期更新 |
| 实时人流 | VisitBeijing MCP | MCP Server 接口 | 实时 |
| 旅游资讯 | VisitBeijing MCP | MCP Server 接口 | 实时 |
| 活动展览 | VisitBeijing MCP | MCP Server 接口 | 实时 |
| 地理信息 | 高德/百度地图 API | API | 实时 |
| 天气 | 和风天气/彩云天气 | API | 实时 |
| 用户评价 | 大众点评/小红书 | 官方 API 或外链跳转 | — |

### 4.3 其他省份占位数据规范
**占位数据定义：** 结构化示例数据，用于演示非北京地区的功能，不声称真实。

**生成方式：**

- 人工构造 JSON/CSV 文件，字段与真实数据结构一致。
- 每个演示省份（如上海、四川、云南、广东）包含 5-10 个景点。
- 每个景点包含：名称、类型、描述、评分、评价数、开放时间、交通、人流等级、官方推荐状态等。
- 评价内容为通用描述，不涉及具体真实商户。
- 官方发布内容为示例公告，标注“演示数据”。

**标注规则：**

- 所有占位数据在 API 返回和前端展示时，必须携带 `data_source: "placeholder"` 字段。
- 推荐理由和置信度中明确提示“该地区为演示数据，建议参考真实平台”。
- B 端看板中，占位数据单独展示，标注“演示”。

**数据加载：**

- 后端维护一个 `placeholder_data` 目录，按省份/城市组织 JSON 文件。
- 当用户查询非北京地区时，系统从占位数据加载，并触发置信度降级。

### 4.4 数据一致性校验

- 北京：多源真实数据交叉验证，方向一致 → 高置信度；分歧 → 中置信度。
- 其他省份：占位数据内部一致，但整体标注低置信度，提示用户参考真实平台。

## 五、技术架构

### 5.1 整体架构
text
```
┌─────────────────────────────────────────────────────┐

├─────────────────────────────────────────────────────┤
```

### 5.2 核心组件
**大模型：** GLM-4 Flash（免费，128K 上下文）

- 对话管理与意图解析
- RAG 生成推荐解释
- 动机画像分析与输出
- 数据源感知与标注

**RAG 管道：**

- 知识库：北京真实景点信息 + 其他省份占位景点信息
- 向量化：text-embedding 模型
- 检索：ChromaDB 向量检索 + 高德 POI API 混合检索
- 生成：检索结果 + 用户画像 + 数据源标注 → GLM-4 Flash 生成推荐

**MCP 集成：**

- VisitBeijing MCP Server 接入，获取北京实时人流、旅游资讯、活动展览数据。

**数据源路由：**

- 根据用户查询的目的地，自动判断使用 L1（北京真实）或 L2（其他占位）数据。

## 九、风险与合规

### 9.1 数据合规

- 用户位置、偏好、行程数据需明确授权，遵循最小必要原则。
- 参考《旅游大数据安全与隐私保护要求》相关标准进行数据采集与存储。
- 用户行为数据采集需获得用户明确同意。

### 9.2 版权合规

- 小红书、大众点评等内容平台数据，优先通过官方 API 获取。
- 如无法获取，采用外链跳转而非数据复制。
- 明确标注数据来源。
- 避免抓取受版权保护的内容。

### 9.3 推荐可信度

- 明确区分“真实数据”与“占位数据”。
- 置信度标注避免用户过度信任低置信度推荐。
- 官方推荐与商业推荐需明确标注，避免利益冲突。
- 其他省份占位数据必须标注“演示数据”，避免误导。

### 9.4 课程作业风险

| 风险 | 应对 |
| --- | --- |
| 数据获取困难 | 北京优先使用已验证可用的 API；其他省份用占位数据 |
| 范围过大 | 架构支持全国，但只做北京真实数据，其他占位演示 |
| 大模型成本 | GLM-4 Flash 免费，控制调用频率 |
| 爬虫合规 | 优先 API，次选外链跳转，最后才考虑模拟数据 |
| 占位数据被误解为真实 | 全链路标注 data_source: "placeholder"，前端明显提示 |

## 十一、答辩演示建议
**核心演示路线：**

1. **用户 A（无动机挖掘）** → 输入“北京 3 天” → 给出故宫、长城、颐和园标准路线。

3. **对比两条路线**，展示动机理解对推荐结果的影响。
4. **展示旅程预演**：点击用户 B 的行程，展示时间线、天气、人流、风险、备选（北京真实数据）。

## 十三、下一步计划
以下方向已在前期讨论中明确价值，但**本版本（V1.2）暂不实现**，作为后续迭代与毕业设计深化方向。

### 13.1 Travelling 事件数据资产化
**核心思路：** 将“一次完整旅行”定义为独立数据类型 `Travelling`，通过 AI 全流程陪伴自动生成事件，上传平台用于推荐，形成“动机→体验→反馈”的数据闭环。

**为什么有价值：**

- 解决旅游推荐的数据稀疏问题：一个 Travelling 事件的信息量相当于几十条单点评价。
- 让 Travel for What 动机数据与实际体验绑定，实现真正的个性化学习。
- 现有平台记录的是“景点”和“评价”，而非“一次完整旅行事件”，这是差异化数据资产。

**事件数据结构（草案）：**

- 身份层：`travelling_id`、`user_id`、`created_at`
- 动机层：`travel_meaning`、`travel_motivation`、`constraints`
- 行程层：`destination`、`duration`、`companions`、`planned_itinerary`、`actual_itinerary`
- 体验层：`places_visited`（含到达时间、停留时长、主观感受）、`deviations`、`highlights`、`lowlights`
- 反馈层：`satisfaction_score`、`recommendation_accuracy`、`would_revisit`、`free_text_feedback`
- 数据来源标注层：`data_source`、`confidence`、`generated_by`

**AI 全流程陪伴采集：**

- 行前：动机画像、约束条件、候选行程选择过程。
- 行中：每个动作同时记录为 trip signal 和 memory event（参考 Wayfarer 的 Live Action to Memory Pipeline）。
- 行后：AI 自动生成事件草稿，用户确认或修正后归档。
- 反馈：事件归档后更新推荐模型。

**用于推荐：**

- 事件相似度匹配（动机、约束、同伴结构、预算）。
- 事件演化图推理（地点访问的顺承关系与路径得分）。
- 动机-体验校准（识别用户声明动机与实际体验偏好的偏差）。

**平台侧闭环：**

- 事件库建设 → 事件聚合推荐 → 文旅局数据看板增加“Travelling 事件视角”。

**课程作业中的 MVP 建议：**

- 必须做：事件数据结构定义、行前动机与计划记录、行后 AI 总结 + 用户确认、简化的事件相似度匹配推荐。
- 可简化：行中实时信号采集（可用模拟数据替代）、事件演化图（用规则替代）。
- 可后置：用户可见性控制、事件聚合分析、B 端事件视角看板。

### 13.2 从游记数据中提炼 Travelling 事件
**核心思路：** 从作家游记等叙事性文本中，自动提炼结构化的 Travelling 事件，作为平台事件库的“种子数据”和“深度内容源”。

**为什么有价值：**

- 游记天然包含动机、行程、体验、情感等完整事件信息。
- 作家游记能提供普通 UGC 缺失的深度观察、历史脉络与文学性描述。
- 可作为冷启动阶段的高质量数据燃料，丰富推荐理由的感染力。

**技术路线（三层递进）：**

**第一层：基于规则的行程链提取（快速上手，效果稳定）**

- 定义触发词表（到达、游览、离开等）+ 地名库，识别行程节点。
- 分析顺序连词（然后、接着、第二天）和句式（从…到…），建立节点次序。
- 生成结构化行程链。
- 参考效果：对 1.7 万篇蚂蜂窝游记实验，提取行程链与人工识别的相似度可达 86.14%。

**第二层：顺承事件图谱构建（进阶，捕捉事件关联）**

- 抽取事件三元组（作者，游览，西湖），构建事件图谱。
- 通过边权重揭示事件的顺承概率（如游览西湖后去灵隐寺的概率 30%）。
- 参考实践：已有开源项目基于 50 万篇携程游记构建顺承事件图谱。

**第三层：基于大语言模型（LLM）的深度事件抽取（前沿，挖掘深层语义）**

- 利用 GLM-4 Flash 设计精细 Prompt，直接抽取结构化 Travelling 事件。
- 研究支撑：TIME 模型利用 LLM 组织旅游信息，事件三元组抽取性能比基线提升 11.1%。
- 独特优势：处理模糊、隐喻、个人色彩描述，提炼情绪、感悟与因果关系。

**差异化价值：**

- 深层动机与意义（如“寻找文化认同”、“精神朝圣”）。
- 深度体验与观察（用于生成更有质感的推荐理由）。
- 历史与文化脉络（为“文化/沉浸”型用户提供深度内容）。

**在平台中的定位：**

- 历史/深度事件的种子库，与 AI 生成的事件互补。
- 冷启动阶段填充事件库；为游记事件打上动机标签，与 AI 事件在同一框架下匹配。
- 推荐景点时引用游记经典描述，增加说服力与感染力。

**实现优先级建议：**

- 课程作业优先实现第一层（规则提取），快速产出可见成果。
- 第二层（事件图谱）作为进阶目标，展示技术深度。
- 第三层（LLM 抽取）作为亮点，处理少量精选作家游记文本进行深度演示。

**挑战与应对：**

- 数据获取与版权：优先使用已进入公共领域的经典游记，或获得授权的文本。
- 文本风格差异：文学性语言对规则方法挑战大，恰好是 LLM 的用武之地。
- 事件粒度与融合：需设计宏观事件与微观事件的对齐与融合机制。

### 13.3 竞品启示与定位强化
当前 AI 旅行助手赛道（同程 DeepTrip、飞猪帮帮、马蜂窝 AI 助手等）强于内容推荐与执行落地，但普遍停留在“标签匹配”阶段，未将“动机挖掘”作为核心交互。地方文旅平台（浙江、广东、湖北等）在数据整合与官方联动上领先，但个性化推荐深度不足。

**Where to Travel 的差异化空间：**

1. **Travel for What 动机挖掘作为核心交互范式**，而非功能增量。
2. **旅程预演（决策预演，非虚拟旅游）**，输出“如果这么走，会遇到什么”。
3. **可解释推荐 + 数据源分层标注**，建立信任。
4. **未来通过 Travelling 事件与游记提炼，构建结构化旅行事件数据资产**，进一步拉开差距。

**答辩时可用的核心话术：**

> “AI 行程规划赛道已经很拥挤，但现有产品解决的是‘怎么去’。我们解决的是‘为什么去’，以及‘去了会怎样’。这不是功能差异，是交互范式的差异。”
> “我们不只记录你去过哪里，我们记录你为什么去、实际体验了什么、以及你的期待和现实之间的差距。每一次旅行都成为一个可复用的数据资产。”
>
